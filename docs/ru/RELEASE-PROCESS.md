# Процесс выпуска

[English version](../RELEASE-PROCESS.md)

Документ задаёт постоянные общепроектные правила подготовки, версионирования,
квалификации, публикации и сопровождения релизов приложения и допущенных
переиспользуемых библиотек. Применяйте его к каждому выпуску, определяя
поддерживаемую область и применимые проверки до начала работ.

## Владение политикой и свидетельствами

| Владелец | Содержание |
|---|---|
| Эта политика | Правила идентичности, совместимости, допуска, продвижения, восстановления и завершения релиза |
| Release notes и записи компонентов | Изменения версии, влияние на оператора/потребителя, обновление, ограничения и ссылки на свидетельства |
| Свидетельства исполнения кандидата | Точные исходники, хеши комплекта, запуски, квалификация цели, блокеры и reviewed решения |
| POM, workflows и tooling | Исполняемые источники версии, триггеры, разрешения, артефакты и валидация |
| Документы возможностей и руководства | Подробные миграции подсистем, эксплуатация и процедуры публикации |
| ADR | Принятые решения и исторический контекст |

Ход кандидата, измеренные результаты и отдельные инциденты публикации хранятся
в соответствующих записях. Меняйте политику при изменении правила проекта.
Новый переиспользуемый компонент следует общим правилам допуска; его история
выпусков и изменяемый перечень компонентов не копируются в этот документ.

[TESTING.md](../TESTING.md) владеет политикой тестов/покрытия;
[SECURITY-ENGINEERING.md](../SECURITY-ENGINEERING.md) — security-контролями,
решениями по уязвимостям и suppressions. Процесс использует эти требования.
Состояние реализации подтверждается свидетельствами, а не выводится из
формулировки политики или имени workflow.

## Модель идентичности релиза

Различайте следующие идентичности:

| Идентичность | Смысл | Источник истины |
|---|---|---|
| Версия продукта, `X.Y.Z[-rc.N]` | Заявление о совместимости приложения | Эффективная версия продукта Maven |
| Tag приложения, `vX.Y.Z[-rc.N]` | Неизменяемые выбранные исходники | Аннотированный Git tag |
| Координата библиотеки | Group, artifact и точная версия компонента/семейства | Допущенный POM компонента и комплект |
| Tag компонента | Неизменяемые исходники одного артефакта библиотеки | Защищённый допуск публикации |
| Ревизия исходников | Полный Git object ID сборки | Разрешённый commit исходников |
| Комплект/digest | Точные квалифицированные файлы и хеши | Build manifest/checksum evidence |
| Runtime build information | Версия, commit и время сборки | Метаданные упакованного приложения |
| Deployment ID | Одна активация на цели | Deployment tooling и свидетельства цели |
| Версия схемы/протокола | Контракт долговременного или wire-формата | Подсистема-владелец |

Цепочка: выбор исходников → сборка → квалифицированные байты → публикация →
активация на цели. Сравнивайте каждое звено с его источником истины.
Версия или deployment ID сами по себе не определяют байты; checksum проверяется
для нужного артефакта из одобренного источника распространения.

Проверки исходников относятся к commit кандидата, бинарные/стендовые —
к точному комплекту и конфигурации цели. Повторная сборка меняет комплект,
если равенство байтов не установлено. Прежние бинарные свидетельства нельзя
незаметно приписывать другим байтам.

## Источник версии продукта

Приложение и внутренние модули разделяют версию продукта. У каждого релизного
семейства один редактируемый источник версии; ресурсы, имена артефактов,
метаданные и тесты получают эффективную версию из сборки. Параллельного
редактируемого `VERSION` нет.

Используйте схему версий, допущенную POM и publication tooling.
[Руководство публикации](../guides/library-publication.md) описывает доступную
реализацию; принятие независимого владения само по себе не активирует
независимые версии Maven.

В режиме общей версии реактора корень владеет CI-friendly revision Maven:

```xml
<version>${revision}</version>

<properties>
    <revision>X.Y.Z-SNAPSHOT</revision>
</properties>
```

Родительские объявления дочерних проектов используют ту же revision:

```xml
<parent>
    <groupId>com.iocextractor</groupId>
    <artifactId>ioc-extractor-parent</artifactId>
    <version>${revision}</version>
    <relativePath>../../pom.xml</relativePath>
</parent>
```

Это фрагменты POM в контексте проекта; для реальной сборки замените пример
версии. Управляемые зависимости реактора в этом режиме используют
`${project.version}`, а не `${revision}`. Глобальный override
`-Drevision`/`LIBRARY_VERSION` версионирует выбранный общий реактор,
а не отдельный компонент. Другая схема требует критериев активации ниже.

## Версии переиспользуемых библиотек

### Владение релизом и совместимость

Библиотеки владеют совместимостью независимо от потребляющего сервиса.
[Каталог](../guides/libraries/README.md), контракты компонентов и
[ADR 0048](../ADR/0048-independent-library-versions-and-reuse.md) определяют
владельцев и связанные семейства. Семейства core/adapter с точной версией
продвигаются вместе: выпуск любого члена выпускает объявленное семейство,
включая неизменившегося партнёра. У каждого артефакта свои исходники/tag,
комплект и квалификация. Требуемый core квалифицируется до адаптера.

Неизменившаяся библиотека не требует выпуска только из-за изменения сервиса.
Потребитель выбирает точную квалифицированную версию и владеет обновлением.
Расположение репозитория, родительская сборка и publication credentials
не определяют совместимость.

Совместимость включает source/binary API, валидацию и отказы,
потокобезопасность/порядок, владение ресурсами, выдаваемые имена/типы и минимальные
требования Java/фреймворка. Проверяйте переносы пакетов, обновления зависимостей
и security fixes на наблюдаемое влияние так же внимательно, как новые API.

Опубликованные версии, включая RC, неизменяемы. Исправление получает новую
версию и tag компонента. Восстановление повторно использует исходные подписанные
файлы и deployment identity, не пересобирает, не переподписывает, не
перезаписывает и не перемещает tag существующей координаты.

### Изменение библиотеки для возможности сервиса

Сначала изучите API и вызывающий код. Используйте подходящий механизм или
расширьте библиотеку-владельца ради ограниченной общей способности. Правила
сервиса, каталоги, схемы, композиция и recovery policy остаются у сервиса;
следуйте [руководству разработки](../guides/libraries/development.md).

Изменения библиотеки и потребителя можно разрабатывать вместе. При независимых
версиях до изменения выпущенного содержимого переведите библиотеку/семейство
на следующую development-версию. При общей схеме используйте допущенную общую
development-версию и записывайте изменение компонента/совместимости.

Перед выпуском сравните с выбранным опубликованным baseline, добавьте
содержательные регрессии, обновите публичный Javadoc и парные руководства,
выполните применимые build/analyzer проверки и изолированных packaged consumers.
Фикстура потребителя — ограниченный свидетель совместимости, а не полный
source/binary API comparison; пробелы реализации принадлежат
[KNOWN-ISSUES.md](../KNOWN-ISSUES.md).

Опубликуйте и квалифицируйте требуемую библиотеку до выпуска потребляющего
сервиса. Закрепите выбранную версию и проверьте итоговую интеграцию.
Локальные исходники реактора не должны незаметно заменять выпущенное содержимое
под той же координатой. Local/SNAPSHOT packaging — свидетельство разработки,
а не опубликованных зависимостей. Авторизация релиза/публикации остаётся явной.

### Активация независимых версий

Переход от общей к независимым исходным версиям требует reviewed реализации,
подтверждающей:

1. Отдельный источник версии каждой библиотеки/семейства и продукта; родитель,
   порядок реактора и dependency management работают с разными версиями,
   неизменившиеся семейства сохраняют версии.
2. Согласованность tag компонента, ancestry исходников, build version,
   flattened/embedded POM, dependency closure и восстановления. Защищённый
   admission не предполагает равенства версии компонента ветке релиза продукта.
3. Сохранение exact-version связи core/adapter, квалификации core первым и
   передачи/восстановления исходного подписанного core.
4. Сервис выбирает нужное выпущенное содержимое при наличии локальных исходников
   библиотек. Квалификация выявляет изменённый код под выпущенной координатой;
   код разработки использует следующую версию.
5. Product-only/library-only сценарии, изолированные потребители, выбранное
   происхождение, хеши и отрицательные version/dependency случаи проходят
   без изменения прежних идентичностей публикации.

Обновляйте владеющие POM/tooling, consumer fixtures, guides, module references
и локальные инструкции вместе. До реализации и квалификации схемы сохраняйте
допущенное поведение общей версии. Состояние перехода принадлежит
[руководству публикации](../guides/library-publication.md) и
[реестру задач](../KNOWN-ISSUES.md), а не формулировке политики как свидетельству исполнения.

## Политика версионирования

Версии используют синтаксис Semantic Versioning:

```text
MAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]
```

Применяйте правила совместимости к продукту или релизному семейству библиотек:

| Изменение | Инкремент |
|---|---|
| Совместимое исправление дефекта/безопасности, документации или внутреннее укрепление | PATCH |
| Совместимая поддерживаемая возможность/API | MINOR |
| Несовместимое изменение поддерживаемого контракта в `0.x` | MINOR с миграционными заметками |
| Несовместимое изменение поддерживаемого контракта начиная с `1.0` | MAJOR с миграционными заметками |

`-SNAPSHOT` обозначает разработку. RC имеет неизменяемую координату
`X.Y.Z-rc.N`; финальная версия — отдельный выпуск, а не перенесённый tag.
У финальной версии нет prerelease suffix. RC не гарантирует совместимость
с последующим final. Каждой библиотеке/семейству требуется явное решение
о стабильном контракте перед `1.0.0`.

Автоматизация приложения допускает более узкий набор `vX.Y.Z` или
`vX.Y.Z-rc.N` с положительным номером RC; общий синтаксис SemVer не означает
поддержки всех suffix/build-metadata форм workflow.

Поддерживаемые контракты приложения включают CLI/options/output/exit codes,
конфигурацию/defaults/preflight, artifacts/manifests, документированные форматы
events/logging, health, обновление/rollback хранилища и установку.
Версию определяет наблюдаемое влияние, а не размер внутренней правки.
Исправления только прозы руководства сами по себе не требуют нового бинарного
выпуска библиотеки.

### Устаревание и удаление

1. Объявите deprecated-контракт, замену и окно миграции в заметках; где возможно,
   обеспечьте стабильное actionable предупреждение runtime.
2. Обычно поддерживайте старый и новый контракты вместе хотя бы один
   опубликованный релиз либо явно объявленное альтернативное окно.
3. Удаляйте позже как breaking/observable change. Удалённые ключи конфигурации
   отклоняются preflight с migration hint вместо тихого no-op.

Экстренное удаление без этого окна требует явной причины безопасности/целостности данных,
breaking-change disposition и действия оператора/потребителя. Версии схем,
manifest, catalog, event и identity принадлежат подсистемам; не приравнивайте
их принудительно к версии продукта.

## Информация о сборке в runtime

Приложение получает идентичность из сборки:

- `spring-boot:build-info` в `bootstrap/ioc-app` создаёт
  `META-INF/build-info.properties`.
- Daemon `/actuator/info` показывает доступные данные сборки.
- Лёгкий `ioc --version` сообщает идентичность без запуска Spring.
- Maven фильтрует ECS `service.version` из `@project.version@`.
- Свидетельства релиза/deployment связывают полный commit, время и digest.

Сборка с известной неизменяемой ревизией передаёт `build.commit`.
Профиль `embed-build-commit` проверяет полный hexadecimal Git object ID и
встраивает его; обычная сборка без свойства пропускает необязательное поле.
Runtime не вызывает Git и не требует `.git`. Упакованная форма:

```text
ioc-extractor X.Y.Z
commit: <first-12-hex-digits>
built: <UTC-build-instant>
```

Необязательные недоступные метаданные могут отсутствовать в IDE/неупакованном
запуске; не выдумывайте fallback-факты релиза. Метаданные не содержат credentials,
локальных source paths и dirty diff. Грязный development deployment может
иметь явную dirty identity, но опубликованные выпуски строятся из чистых
выбранных исходников.

## Ветки и tags

Tags выбирают исходники релиза; ветки описывают рабочий процесс.

- У integration, stabilization и maintenance веток явные владельцы и цели
  поддержки/backport. Релизная ветка не доказывает публикацию.
- Приложение использует аннотированные `vX.Y.Z`/`vX.Y.Z-rc.N` для final/RC.
- Tag компонента следует protected admission и выбирает квалифицированные
  исходники своего артефакта.
- Не перемещайте, не удаляйте и не используйте повторно опубликованный tag.
  Исправления получают новую версию/tag.
- Обязательные проверки/review защищают допустимые исходники; защита
  tag/environment предотвращает неавторизованное продвижение.

Проверяйте эффективные внешние настройки репозитория до заявления об их
применении; текст workflow не доказывает branch/tag protection.

## Артефакты релиза

| Семейство | Обязательные идентичность и содержимое |
|---|---|
| Приложение | Аннотированный source tag, curated notes, `ioc-extractor-X.Y.Z.jar` и sidecar `.sha256` |
| Библиотека | Допущенные coordinate/tag, независимый от родителя POM, main/sources/Javadoc и license, manifest/checksums, требуемые подписи и repository qualification |

Дескрипторы компонентов и [руководство публикации](../guides/library-publication.md)
владеют точными файлами/зависимостями библиотек. Source archives дополняют
проверенный JAR приложения и не заменяют его. Дополнительные signing, SBOM
и attestation приложения обязательны после принятия с определёнными
trust/consumer и verification workflow. Требования signing репозитория
библиотек остаются в своём publication contract.

Соберите один квалифицированный комплект и продвигайте точные байты между
draft, release, стендом и production. Несколько development-сборок допустимы;
новому комплекту нужны собственные применимые бинарные свидетельства.
Одинаковые source/version не доказывают воспроизводимость байтов разных запусков.

## Контракт release notes

### Заметки приложения

Скопируйте [TEMPLATE.md](../../.github/release-notes/TEMPLATE.md) в
`.github/release-notes/<application-tag>.md`. Tag workflow читает файл
из выбранных исходников. Сохраняйте обязательные разделы по порядку; если
содержание неприменимо, указывайте явное `Not applicable`:

```markdown
# IOC Extractor X.Y.Z

## Highlights
## Added
## Changed
## Fixed
## Upgrade notes
## Breaking or observable contract changes
## Known issues
## Verification
## Artifacts and checksums
```

Далее допустим необязательный `Technical references`. Заметки объясняют
результат для пользователя/оператора, а не темы Git, содержание ADR или весь
реестр долга. Для каждого observable/breaking изменения укажите: что поменялось,
кто затронут, автоматическую миграцию, требуемое действие и поддержку rollback.
Объясните prerequisites, backup/recovery unit и проверку после обновления.

Для machine-readable изменений включайте минимальные before/after payloads
и parser/query examples, когда уместно. Различайте field/path, физическую форму,
scalar type и presence/value semantics: неизменные имена не доказывают совместимость.

Записывайте фактическую область проверки, недоступные внешние проверки
и approved dispositions. Точные финальные commit/digest/run identities помещайте
в полученные свидетельства; не угадывайте до появления кандидата. Связывайте
существенные пользователю известные проблемы и меры снижения риска.
Не включайте секреты или чувствительные данные оператора.

Предпочитайте PR/issue, затем обоснование ADR, один полный compare range
и raw commit только при полезности точного перехода. Tag, packaged identity
и digest задают релизную идентичность; commit-ссылка на каждый пункт не нужна.

`make release-notes-context PREVIOUS_TAG=vX.Y.Z TARGET_REF=HEAD` создаёт
read-only inventory; `GITHUB=1` добавляет подходящие merged PRs. Генерируемые
перечни/заметки — вход для подготовки текста с человеческим review совместимости
и operator impact. Исторические imports явно помечаются и не переписывают
неизменяемые tags или опубликованные notes; исключения архива описаны в
[справочнике заметок](../../.github/release-notes/README.md).

### Записи релизов компонентов

У библиотек записи уровня компонента, без application title и принудительной
копии шаблона приложения. Укажите coordinate/family, source/tag, supported
API/dependencies, compatibility/migration, исходный manifest/signed bundle,
repository consumers и неполную qualification/recovery.

[Каталог](../guides/libraries/README.md) и
[руководство публикации](../guides/library-publication.md) ведут к записям
и правилам их именования. Запись различает исходную публикацию, восстановление
и поздние consumer evidence без изменения неизменяемых идентичностей.

## Жизненный цикл релиза

### 1. Планирование и стабилизация

Выберите область product/component/family, версию и поддерживаемые пути
обновления. Определите блокеры, критерии приёмки и reviewed deferrals.
Проверьте наблюдаемые поверхности, миграции и границы rollback. Разработка
сохраняет допущенную схему `-SNAPSHOT` до подготовки кандидата.

### 2. Подготовка релизного commit

Задайте точную final/RC версию, обновите документы и notes, согласуйте
производные метаданные/артефакты. Определите нужные библиотеки и квалифицируйте
их выбранное содержимое до выпуска потребляющего продукта. Зафиксируйте
чистые исходники и предоставьте обязательному CI; ход кандидата принадлежит
его свидетельствам.

### 3. Проверка качества

Используйте полные принятые проверки, а не выбранный быстрый suite:

```bash
make verify
make pmd-analysis
make docs
make lint-shell
git diff --check
```

[TESTING.md](../TESTING.md) и [качество сборки](../dev/build-quality.md)
определяют coverage, analyzer policies, целостность отчётов и свежесть.
Квалифицируйте точные исходники кандидата; после правок повторите затронутые
проверки и итоговые обязательные gates.

Также получите применимые security evidence по
[политике безопасности](../SECURITY-ENGINEERING.md), проверки packaged
identity/help/version и runtime smoke, свидетельства supported migration/rollback,
целевые внешние проверки и library compatibility/packaged/repository consumers.
Определяйте применимость до релиза и явно решайте судьбу недоступных проверок.
Рекомендательная отчётность не заменяет блокирующие проектные контроли.
Reviewed dispositions допустимы только по контракту-владельцу; неуспешный
блокирующий gate остаётся блокером до исправления или явного изменения через
проектный процесс решений по политике/области.

Source gates могут собирать development-артефакты. Финальная бинарная
квалификация относится к реально продвигаемому комплекту. Не считайте,
что один release workflow автоматизирует все независимые security, analyzer
и стендовые требования.

### 4. Создание source release

После обязательных проверок исходников создайте допущенный аннотированный tag
на выбранном commit. Версия должна совпадать с эффективной build version.
Сохраняйте tag/source identity во всей публикации и восстановлении.

### 5. Однократная сборка и публикация

[Workflow приложения](../../.github/workflows/release.yml) определяет точные
source/tag/version, проверяет annotation и commit selection для draft,
внедряет source identity, выполняет один `clean verify`, отклоняет изменение
дерева исходников и сверяет packaged build metadata с лёгким выводом версии.
Он один раз подготавливает JAR/checksum и передаёт байты отдельной write-enabled
job без Maven-сборки.

Ручной build-only dispatch проверяет/собирает выбранный ref и сохраняет workflow
artifacts, не создавая release. Draft mode требует совпадения существующего
названного tag с checkout commit. Tag push следует draft mode.
Retention и точные inputs принадлежат workflow.

[Draft helper](../../packaging/publish-release-draft.sh) проверяет переданные
version/files/checksum/notes и создаёт/восстанавливает только draft.
Source/tag admission принадлежит workflow. Имеющиеся обязательные артефакты
скачиваются и сравниваются побайтово; несовпадение приводит к отказу без clobber.
Опубликованные releases доступны автоматизации только на чтение. Повторный
запуск с другими собранными байтами не восстанавливает исходный комплект
и не может использовать его бинарные свидетельства.

[Публикация библиотек](#library-publication) следует отдельному защищённому workflow.
Публикация — явно авторизованное продвижение после review notes, артефактов
и обязательных свидетельств; сборка комплекта или принятие ADR её не разрешает.

### 6. Deployment и проверка

Квалифицируйте точный комплект кандидата на требуемом стенде до публикации,
если это предусмотрено планом; продвигайте на цели те же одобренные байты.
Используйте поддерживаемый [протокол packaging](../../packaging/README.md),
проверяйте checksum до изменения host и сравнивайте установленную версию,
полный commit исходников, deployment ID, digest, build information и локальное
здоровье storage/artifacts.

Версия релиза сама по себе не доказывает совместимость installation layout,
конфигурации или схемы. Явно согласуйте operator configuration, проверьте
кандидатом в эффективной service environment и сохраните оговорённую единицу
backup/restore. Новые template files не мигрируют установленную конфигурацию
автоматически.

Deployment из checkout собирает свой идентифицированный комплект и не
доказывает развёртывание опубликованного JAR. Отличайте optional remote
degradation от локального отказа активации по deployment health contract.

### 7. Завершение и развитие

Запишите авторизованную публикацию, неизменяемые tag/assets, требуемую
квалификацию и оставшиеся решения. Merge/backport release-only fixes выполняются
в поддерживаемом порядке; выберите следующую development-версию, наблюдайте
окно deployment и выпускайте новую версию для исправлений. Состояние публикации
и завершение всех обязательств приёмки остаются отдельно наблюдаемыми.

## Политика rollback и hotfix

Каждое поддерживаемое обновление до активации описывает границу rollback:
только переключение binary, согласованное восстановление, side-by-side migration
или явно неподдерживаемый rollback. Квалифицируйте утверждение на
репрезентативном прежнем состоянии; additive migration или здоровый startup
сами по себе не доказывают поддержку.

Recovery point приложения включает согласованные приложение, operator configuration,
systemd/unit state и обе SQLite БД с консистентной процедурой резервирования.
Сохраняйте соответствующие side files, permissions и ownership по packaging.
Не копируйте живой SQLite-файл обычным filesystem copy в предположении,
что результат консистентен.

Deployment automation восстанавливает только свой описанный scope.
Configuration reconciliation, перемещённые входные файлы, projections/slices
и завершённые удалённые эффекты могут требовать отдельного восстановления.
При rollback-sensitive qualification приостановите intake/sync; автоматический
локальный rollback не обращает удалённые эффекты.

Для hotfix воспроизведите/классифицируйте дефект, исправьте поддерживаемую линию,
выполните обычные gates, выпустите новый совместимый patch или подходящую
breaking version и опишите исправление уже обновлённых data/configuration.
Не заменяйте JAR или Maven-файлы существующей версии.

## Критерии завершения

Закрывайте релиз продукта/компонента, когда:

- Явны scope, supported contracts и upgrade/rollback paths.
- У продукта/семейства один эффективный источник версии.
- Обязательные блокирующие gates успешны, exact-bundle/target qualification
  удовлетворяет своему acceptance contract только с разрешёнными reviewed dispositions.
- Notes/docs объясняют наблюдаемые изменения, действия и оставшееся влияние.
- Неизменяемые source/tag, packaged metadata, bundle hashes и repository origin согласованы.
- Требуемые artifacts/signatures/checksums присутствуют и проверены.
- Публикация авторизована, незаписанных релизных блокеров нет.
- Есть deployment/recovery evidence для заявленных поддерживаемых путей.
- Записаны дальнейшее development ownership и post-release follow-up.

Сборка, публикация и deployment — разные результаты. Один RC, локальный
consumer, успешная отправка или обновление документации не подтверждают их все.

## Дальнейшая автоматизация

Новой проверке до превращения в релизное требование нужны владелец, потребитель,
контракт верификации и сохранённые свидетельства. Примеры: authenticity/
attestation приложения, composition transparency/SBOM, активация независимых
версий, автоматизация backports, помощь с changelog и сравнение воспроизводимых
сборок. Статус принятия принадлежит реализации и реестру задач. Не описывайте
план как действующий контроль и не ослабляйте принятый контроль незаметно.

## Публикация библиотек

Используйте отдельный [защищённый workflow](../../.github/workflows/library-publication.yml)
и дескрипторы компонентов в [publication tooling](../../tools/ci/library-publication.py).
Каталог определяет допущенные компоненты; добавление библиотеки требует явного
source/version admission, области dependencies/API, package/license/docs checks,
подписанного неизменяемого комплекта, изолированных consumers и repository qualification.

Публикуйте одинаковые файлы в требуемые репозитории. Проект использует Maven
Central основным и GitHub Packages для тех же байтов; проверяйте selected origin
и хеши каждого заявленного репозитория. Успех alternate cache/repository не
маскирует отсутствие выбранного артефакта или transitive dependency.

Exact-version семейства квалифицируют core до adapter, сохраняют отдельные
записи артефактов и передают исходный подписанный core при публикации/
восстановлении adapter. Частичная публикация продолжается из исходных подписанных
файлов и repository evidence. Релиз следующего компонента не меняет tag,
байты или историю квалификации прежнего.

Flattened consumer POM не требует приватного родителя реактора; валидируемые
third-party зависимости и application-owned backends сохраняют своих владельцев.
Автоматизация приложения не публикует библиотеки Maven. Подробные команды,
активные ограничения допуска и recovery procedures принадлежат
[руководству публикации](../guides/library-publication.md), решения —
[ADR 0028](../ADR/0028-pilot-library-publication.md),
[ADR 0029](../ADR/0029-release-branch-library-publication.md) и
[ADR 0048](../ADR/0048-independent-library-versions-and-reuse.md).
