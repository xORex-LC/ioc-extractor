# Включение маршрутов обработки IOC

[English version](../ioc-processing-routes.md)

Каждый документ использует именованный план обработки; каждый контракт импорта
`processed` должен явно выбрать план. Поставляемый `original-document`
маршрутизирует полные исходные значения IOC и сохраняет учёт исходных наблюдений.
Отображение артефакта, канонические ключи и политики записи задаются отдельно.
Новый маршрут меняет будущую обработку, не переписывая существующие строки.

## Сначала выберите выходной контракт

Определите, какие поля требуют чистый хост, а какие сохраняют полный
восстановленный адрес. Для плана `customer-hosts` из этого руководства одни
наблюдения документа дают:

| Входное наблюдение | `masks.mask` | `address_blacklist.forbidden_url` |
|---|---|---|
| `hxxps[:]//best-malware[.]com/troyan.exe` | `best-malware.com` | `https://best-malware.com/troyan.exe` |
| `https://best-malware.com/other.exe` | `best-malware.com` | `https://best-malware.com/other.exe` |

Два кандидата маски по хосту сводятся к одному итоговому ключу, а чёрный список
сохраняет оба адреса. С поставляемым отображением `10.93.12.187:9090/path` даёт
`ip_list.ip = 10.93.12.187`, исходное представление чёрного списка сохраняет
полный адрес в `forbidden_url`. Чистый IP исключается из `masks`. Хеши остаются
в отдельной ветви, их поля используют настроенное преобразование в верхний регистр.

`network.host` создаёт хост/IP без изменения `original`. Отдельное преобразование
отображения `lower-host` приводит схему и хост к нижнему регистру, сохраняя
регистр пути, запроса и фрагмента; оно не удаляет порт или путь. Классификация
каждого выбранного представления по-прежнему использует `ioc.classify.rules`.
Перед выбором представления изучите фактические колонки и идентичность.

## Подготовьте полный candidate

Начните с текущего полного YAML установки. Сохраните существующие артефакты,
определения идентичности, учётные данные, контракты импорта и каждый именованный
план, на который ссылается документ или импорт. `ioc.processing.plans` — список:
Boot заменяет его целиком, не добавляя и не объединяя планы по именам.

Следующий блок показывает новый план и его селектор документа. Добавьте план
в существующий список полного candidate и измените селектор; не заменяйте список
этим фрагментом, если действующим контрактам нужны другие планы. Например,
production template привязывает объявленный контракт импорта агрегата к
`original-aggregate-import`, даже при отключённом приёме. Ниже покрыты все
включённые артефакты документа; адаптируйте набор к своему каталогу.

```yaml
ioc:
  processing:
    document-plan: customer-hosts
    plans:
      - name: customer-hosts
        observation-selection: final-key
        views:
          - { name: host, operation: network.host, input: original }
        classifications:
          - { view: original, policy: configured }
          - { view: host, policy: configured }
        routing:
          mode: all
          on-unmatched: { action: skip }
          branches:
            - id: masks-host
              artifact: masks
              default-view: host
              eligibility:
                'on': original
                predicate: type-in
                arguments: { types: [IPV4, DOMAIN, URL] }
            - id: ip-host
              artifact: ip_list
              default-view: host
              eligibility:
                'on': original
                predicate: type-in
                arguments: { types: [IPV4, DOMAIN, URL] }
            - id: blacklist-original
              artifact: address_blacklist
              default-view: original
              eligibility:
                'on': original
                predicate: type-in
                arguments: { types: [IPV4, DOMAIN, URL] }
            - id: hashes-original
              artifact: hashes
              default-view: original
              eligibility:
                'on': original
                predicate: type-in
                arguments: { types: [MD5, SHA1, SHA256] }
            - id: aggregate-original
              artifact: ioc_aggregate
              default-view: original
```

`observation-selection: final-key` заставляет кандидатов по хосту конкурировать
по итоговой отображённой идентичности артефакта. Это также значение по умолчанию
для нового плана; явное указание делает схлопывание в примере осознанным.
Поставляемый план исходных значений использует `retained-observations`, сохраняя
учёт исходных вхождений, ID и происхождения. Ни один режим не заменяет
долговременную межзапусковую дедупликацию.

После выбора ветви `accepts` и включающие/исключающие фильтры артефакта всё ещё
проверяют её представление по умолчанию. Затем каждая колонка использует своё
представление для условий типов, остальных условий, поставщика и преобразований.
Колонка из `field-views` может читать `original`, даже если ветвь использует
`host`. Поставщик `const` остаётся константой; поставщики источника и ID не
перепривязываются. Отключённый артефакт нельзя маршрутизировать, включённый
артефакт документа должен быть либо маршрутизирован, либо перечислен в
`omitted-artifacts`, но не одновременно. Пропуск не означает удаление его старых строк.

## Выбор ветвей и недоступный вход

| Режим маршрутизации | Поведение выбора |
|---|---|
| `first` | Проверяет ветви по порядку и выбирает первое совпадение. Достигнутое заблокированное условие останавливает выбор до последующих ветвей. |
| `all` | Выбирает все подходящие ветви по порядку; сообщает заблокированные ветви вместе с выбранными. Фактическую запись всё ещё определяет прикладная политика отказов. |
| `exclusive` | Требует ровно одно совпадение; второе отклоняет выбор. Достигнутое заблокированное условие также мешает успешному выбору. |

Условие — один лист (`on`, зарегистрированный `predicate`, применимые
`arguments`) либо одна группа `all`, `any` или `not`. Группы досрочно замыкаются
в объявленном порядке. Заключайте `'on'` в кавычки YAML, как в примере, чтобы
инструменты YAML 1.1 не считали ключ логическим значением. Отсутствующее условие
выбора ветви означает безусловное выполнение.

Политика `on-unmatched` применяется к обычному отсутствию совпадений: `skip`
не выдаёт кандидата, `reject` даёт ошибку маршрутизации, `route` выбирает явно
именованную `default-branch`. Резервная ветвь не имеет условия выбора.
Недоступное обязательное представление не является обычной ложью и не становится
истиной под `not`; резервный маршрут не восстанавливает ошибки автоматически.
Даже после выбора недоступные обязательные представления колонок могут
блокировать назначение. Остальные назначения могут подготовить кандидатов,
которые затем подчиняются checkpoint.

Некорректная адресная часть и неподдерживаемые формы дают типизированную
недоступность. Явный `view.recover` создаёт отдельное именованное представление:
`input` задаёт предпринятое представление, `arguments.on-reasons` разрешает
зарегистрированные причины, зависящие от входа, а `arguments.use-view` именует
альтернативу. Восстанавливайте только там, где альтернатива допустима для
выходного контракта. Успешное восстановление даёт предупреждение, если
восстановлены все достигнутые потребители этой ошибки; любой невосстановленный
потребитель сохраняет ERROR. Изменение политики отказов не создаёт альтернативу.

Допуск реестра ограничивает сложность планов, представлений, ветвей и условий
и отклоняет неизвестные операции, ссылки и недопустимые привязки. Конфигурация
не внедряет URI endpoints Camel, скрипты и произвольный язык выражений.
Поддерживаемые ключи перечислены в
[справочнике конфигурации](../configuration.md#ioc-processing-plans).

## Привяжите контракт processed-импорта

Для контракта, отображающего CSV-колонку `ioc` в `masks.mask`, добавьте следующий
отдельный план в тот же полный список. В нём одна разрешённая ветвь артефакта;
пятиветочный документный пример нельзя без изменений применять к контракту
только masks. План — элемент списка, а не полная конфигурация приложения:

```yaml
name: import-hosts
views:
  - { name: host, operation: network.host, input: original }
classifications:
  - { view: original, policy: configured }
  - { view: host, policy: configured }
routing:
  mode: all
  on-unmatched: { action: reject }
  branches:
    - id: imported-mask
      artifact: masks
      default-view: host
```

Соответствующий фрагмент внутри контракта:

```yaml
processed-route:
  plan: import-hosts
  inputs:
    - { artifact: masks, target: mask }
  outputs:
    - { artifact: masks, targets: [mask] }
```

Явно сохраните распознавание, отображение, полномочия источника, слияние и политику
отказов строк контракта. Каждый вход и выход маршрута именует отображённую
ячейку контракта; маршрут не заменяет полномочия источника и не создаёт вторую
ветвь того же артефакта. Фрагмент разрешает только выход `mask`: вычисленные
при подготовке коды классификации не импортируются автоматически, если
контракт дополнительно не отображает и не разрешает их выходные колонки.

Каждый выбранный VALUE восстанавливается, очищается от окружающих пробелов и
должен содержать ровно один полный IOC. Текст вокруг IOC, несколько совпадений
и некорректные сетевые адреса отклоняются. ABSENT, явный NULL и VALUE сохраняют
различия; отсутствие вклада поставщика не является явным CSV NULL. Конфликтующие
вклады отдельных входов отклоняют составную логическую строку. `as-is` пропускает
маршрутизацию IOC, сохраняя объявленные преобразования и валидаторы.
Контракт `processed` без маршрута не проходит допуск конфигурации и при
отключённом приёме.

Для удаления только HTTP(S) в одном сценарии импорта объявите
`{ name: scheme-free, operation: network.without-scheme, input: original }`
в отдельном плане, классифицируйте `scheme-free` и выберите его для разрешённых
полей или ветви. `https://example.com:8443/Path?q=One#Part` превращается в
`example.com:8443/Path?q=One#Part`; чистый вход принимается без изменений.
Операция сохраняет суффикс, после чего применяются обычные преобразования
артефакта. Неподдерживаемые схемы и некорректные адреса остаются типизированными
отказами. Меняются только планы, выбирающие представление; правка общего
`ioc.sink.artifacts[].columns[].transform` затрагивает все обработанные пути
этого артефакта.

Перед подачей проверьте репрезентативный CSV через
[`ioc import validate`](../dataframe-import.md#validate-without-importing) с
`--source` и `--file`. Предпросмотр требует настроенный разрешённый набор
источника и включённый граф проверки импорта; он не доказывает результат
будущего коммита при изменившемся каноническом состоянии.

## Включение и восстановление

1. Приостановите производителей и завершите незаконченные допуски и захваченные
   документы и незапечатанные закреплённые доставки импорта по старой политике.
   Не возвращайте принадлежащие сервису файлы вручную во входной каталог.
   Барьер документа использует полный отпечаток обработки, поэтому даже
   изменение другого объявленного плана может потребовать завершения очереди.
   Незапечатанный импорт нельзя повторно подготовить с изменённым закреплённым контрактом.
2. После завершения очереди остановите сервис и создайте согласованную копию
   обеих SQLite БД и принадлежащих сервису файлов с соответствующими
   конфигурацией и бинарём. Следуйте [процедуре развёртывания](deployment.md);
   независимое копирование работающих БД и sidecars не даёт согласованную точку восстановления.
3. Подготовьте полный candidate, как описано выше. Выполните установленные
   `ioc-config check` и `ioc-config apply` через `sudo` по
   [процедуре конфигурации](configuration.md#how-configuration-is-applied).
   Успешная предварительная проверка не квалифицирует сохранённую политику и
   состояние восстановления. Возврат YAML после неудачной активации не отменяет изменения БД.
4. Используйте `ioc extract --source ... --dry-run` для диагностики чтения и
   подготовки и предпросмотр репрезентативного processed CSV. Dry run не
   резервирует ID, не записывает канонические строки и проекции; он всё ещё
   читает и подготавливает данные, не обещая отсутствия рабочего ввода-вывода.
   Предпросмотр и dry run не квалифицируют последующие сохранение и доставку.
5. Подайте небольшой контролируемый вход и сравните значения, метки источников,
   коды классификации, число идентичностей и CSV каждого затронутого артефакта.
   Проверьте `ioc health` и диагностику. `COMPLETED_WITH_ERRORS` возвращает код
   extract `3`; `collect-and-continue` уже мог записать корректные строки.
   Предупреждения сами по себе не означают отказ. Техническая трассировка
   маршрутов не содержит значений; необязательный TRACE элементов может содержать IOC и сведения об источниках.

Существующие строки сохраняют старые ключи. При фиксированном сроке действия
они истекают по прежнему TTL; отключённый жизненный цикл не обещает истечения.
Коммиты документа остаются поартефактными: поздний отказ может сохранить
предыдущие коммиты. Управляемый импорт продвигает принятые изменения в одной
межартефактной транзакции dataframe и завершается по канонической квитанции
после сбоя за коммитом. Автоматического перерасчёта сохранённых строк и
исполнителя старых планов нет. Последующая смена плана требует тех же правил
завершения очереди, проверки и восстановления.
