# Разработка и версионирование переиспользуемых библиотек

[English version](../../libraries/development.md)

Это руководство нужно, когда фича сервиса использует одну из
[общих библиотек](README.md), в том числе если её API требуется доработать.
[ADR 0048](../../../ADR/0048-independent-library-versions-and-reuse.md)
сохраняет принятое решение. Правила версий определяет
[процесс выпуска](../../../RELEASE-PROCESS.md#reusable-library-versions),
операции публикации — [отдельное руководство, EN](../../library-publication.md).

## Текущее состояние и принятое направление

Независимые версии библиотек приняты как целевая схема. Concurrency, diagnostics,
logging и configuration получат собственные версии выпуска. Events core и
Spring-адаптер сначала сохранят общую версию семейства: адаптер требует точно
такую же версию core, который публикуется первым. Выпуск любого участника
семейства повышает обе версии и выпускает оба артефакта, даже если реализация
одного не менялась. Внутренние модули IOC сохраняют версию сервиса.
Каждый сервис выбирает момент обновления зависимости; изменение
IOC само по себе не требует выпуска неизменившейся библиотеки.

Технический переход **ещё не выполнен**. Исходные POM по-прежнему наследуют
`${revision}` продукта, а допуск публикации сверяет версию компонента с веткой
`release-X.Y.Z`. До закрытия [TOOL-9](../../../KNOWN-ISSUES.md) действует текущая
процедура. Другое значение `LIBRARY_VERSION` или глобальный `-Drevision` не
обеспечивают независимого версионирования. Опубликованные артефакты и теги
`0.3.0-rc.1` сохраняют свои идентификаторы.

## Сначала найдите готовый инструмент

Начните с каталога, затем прочитайте руководство библиотеки, README модуля и
публичный Javadoc. Изучите реализацию, тесты и существующие вызовы, прежде чем
решать, что нужного API нет. Ищите по поведению, а не только по предполагаемому
имени класса.

Например, выполнение по ключам нужно сопоставить с concurrency, ограничение
подробностей диагностик — с diagnostics, типизированные логи и восстановление
MDC — с logging, проверку имён настроек — с configuration, публикацию локальных
управляющих событий — с events. Проверяйте ограничения: выполнение по ключам
локально для процесса, публикация событий не обеспечивает надёжную доставку,
а инспекция конфигурации не выбирает политику запуска сервиса.

| Что обнаружено | Что делать |
|---|---|
| Готовый API покрывает требование | Использовать его и проверить интеграцию сервиса. |
| API подходит, но сервису нужна своя политика или сборка компонентов | Скомпоновать его локально, сохранив политику в сервисе. |
| Дефект или небольшая общая возможность относятся к библиотеке | Изменить библиотеку и её потребителей вместе. |
| Требование выходит за ответственность или границы зависимостей библиотеки | Оставить его в сервисе либо подходящем адаптере и объяснить границу. |

Не копируйте класс библиотеки, не создавайте параллельный helper и не добавляйте
другую зависимость ради обхода подходящего общего API или его доработки.
Наличие библиотеки также не оправдывает абстракцию для гипотетических задач или
зависимость на Spring в модуле только с JDK. Для исправления или развития уже
выделенной библиотеки не требуется ждать второго развёрнутого сервиса.

## Разработка изменения библиотеки вместе с фичей

1. Опишите недостающее поведение и причину его размещения в библиотеке.
   Определите затронутые публичные контракты и существующих потребителей.
   Каталоги сервиса, схемы настроек, бизнес-правила, долговечное состояние и
   решения о восстановлении сохраняйте вне библиотеки.
2. Выберите следующую версию разработки по правилам выпуска. После активации
   независимых версий изменяемая библиотека или семейство events переходит на
   следующую `-SNAPSHOT`-версию. До этого используйте текущую общую версию
   разработки и фиксируйте предполагаемое изменение компонента; подмена версии
   продукта не заменяет технический переход.
3. Реализуйте изменения библиотеки и сервиса вместе. Допустимы одна ветка и
   один PR. Отдельные логические коммиты упрощают проверку общего контракта и
   его интеграции; отдельный PR библиотеки необязателен.
4. Проверьте успешное поведение, ошибки, границы и восстановление. Исправление
   дефекта сопровождается регрессионным тестом. Сопоставьте совместимость
   исходного кода и бинарного API с выбранной опубликованной версией, а также
   поведение, не выраженное сигнатурами. Автоматическое сравнение API остаётся
   открытым TOOL-6; успех текущих consumers не является полным сравнением.
5. В том же изменении обновите содержательный публичный Javadoc, README модуля
   и оба языка руководств. Исполняемые блоки должны совпадать. Явно укажите
   отличия от опубликованной версии: новый метод из разработки ещё недоступен
   в старом артефакте. При необходимости опишите обновление и миграцию.
6. Запустите точечные тесты, затем `make verify` и `make pmd-analysis`, если
   менялся production Java или область анализаторов. Перед публикацией
   подготовьте новый локальный комплект и выполните подходящий изолированный
   consumer по руководству публикации. Локальная упаковка и проверка
   опубликованного репозитория — разные результаты.

Чтобы продолжать фичу, публикация не нужна. SNAPSHOT и сборки реактора дают
обратную связь при разработке; выпускаемый сервис фиксирует проверенные
неизменяемые зависимости. Тесты, коммит фичи или правка документации сами по
себе не разрешают публикацию артефактов либо выпуск сервиса.

## Выпуск и обновление потребителя

Опубликуйте нужную версию библиотеки, проверьте её отдельно из Central и
GitHub Packages, затем зафиксируйте эту версию в сервисе и проверьте итоговую
интеграцию перед его выпуском. Для events сначала проверяется core; адаптер
получает именно этот выпущенный core и сохранённые свидетельства проверки.
Теги компонентов и комплекты артефактов остаются отдельными.

Например, после технического перехода дополнение API diagnostics можно
разработать как `0.4.0-SNAPSHOT`, опубликовать как `0.4.0` и подключить в выпуск
IOC с другим номером. Это пример, а не инструкция текущей публикации. Другой
сервис может оставаться на прежней поддерживаемой версии diagnostics до своего
обновления.

Совместимые исправления повышают PATCH, совместимые дополнения API — MINOR.
В линейке `0.x` несовместимые изменения поддерживаемого контракта повышают MINOR
и требуют описания миграции. Начиная с `1.0`, несовместимость повышает MAJOR.
Правила `0.x` — явное обязательство проекта; сам номер не делает API стабильным.
Повышение минимальной Java или версии фреймворка, изменения ошибок,
потокобезопасности и типов полей в логах также требуют проверки совместимости.

Любой выпуск, включая RC, неизменяем. Исправление опубликованной версии получает
новый номер и тег компонента. Незавершённую публикацию восстанавливают из исходных
подписанных файлов с тем же идентификатором развёртывания Central. Исправление
только текста руководства не требует бинарного выпуска. Обновление зависимости
одного сервиса не обновляет остальные автоматически.

## Что указывать в описании изменения

Назовите переиспользованный или расширенный API, причину локальной альтернативы,
влияние на совместимость и выбранные версии. Укажите затронутых потребителей,
тесты и документацию. Различайте локальную сборку/упаковку и реальную проверку
репозитория. Незавершённую реализацию или проверку совместимости фиксируйте
отдельно, не объявляя выполненной.

## Источники истины и поддержка документа

- [Правила выпуска](../../../RELEASE-PROCESS.md#reusable-library-versions) и
  [ADR 0048](../../../ADR/0048-independent-library-versions-and-reuse.md):
  владение версиями, их изменение и критерии активации.
- [Корневой POM](../../../../pom.xml),
  [допуск публикации](../../../../.github/workflows/library-publication.yml) и
  [проверки упаковки](../../../../tools/ci/library-publication.py): фактическая
  реализация. Сейчас они сохраняют общую версию.
- [Каталог библиотек](README.md): предоставляемые инструменты и границы.
- [KNOWN-ISSUES](../../../KNOWN-ISSUES.md): автоматизация совместимости TOOL-6
  и технический переход на независимые версии TOOL-9.

Обновляйте оба языка при изменении владения, совместимости, разработки или
публикации. Объявляйте независимые версии действующими только при наличии
свидетельств проверки POM, допуска публикации, зависимостей и consumers.
Постоянные факты выпуска сохраняются в записи компонента, решения — в ADR.
