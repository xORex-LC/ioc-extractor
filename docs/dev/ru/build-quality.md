# Качество сборки

[English version](../build-quality.md)

Качество сборки — принадлежащая репозиторию возможность Maven. Канонический
жизненный цикл `verify` компилирует и тестирует реактор, проверяет модульные и
архитектурные правила, анализирует production-код и строит агрегированные отчёты.
Каждая принятая статическая проверка требует актуального и полного результата.
Политики различаются: часть находок блокирует сразу, часть остаётся
диагностической, но отказ анализатора или целостности отчёта принятой проверки
не превращается незаметно в успешную сборку.

Документ объясняет устойчивую механику и её сопровождение. Снимки релизов,
история версий инструментов, текущие количества и отдельные решения по находкам
принадлежат исполняемой конфигурации, versioned baseline и генерируемым отчётам.

## Поток сборки

Локальная сборка и CI используют одну точку входа Maven:

```text
make verify
  -> tools/ci/build.sh
  -> ./mvnw -B -ntp -T 1C verify
       |
       +-- root validate
       |    compile JDK-only quality verifiers
       |    run their synthetic-reactor contract matrices
       |    reconcile reactor modules with SpotBugs/CPD/PMD scope manifests
       |    validate test discovery/source inventory and coverage topology
       |    validate the accepted SpotBugs baseline and generate its filter
       |
       +-- initialize
       |    remove stale test, coverage and analyzer outputs
       |
       +-- ordinary reactor lifecycle
       |    compile -> test -> package
       |    Maven Enforcer + ArchUnit + documentation contracts
       |    module JaCoCo and raw SpotBugs reports
       |    filtered SpotBugs presentation reports
       |
       +-- final build-support modules
            JaCoCo aggregate + exact test-report union + coverage policy
            raw and filtered SpotBugs aggregates + exact baseline gate
            repository-wide PMD CPD report + exact group-count ratchet

successful Maven build
  -> revalidate the Codecov aggregate input

CI build completion (success or failure)
  -> upload test, coverage, SpotBugs and CPD evidence even when the build failed late

successful CI build
  -> separate least-privilege reporting job downloads the verified artifact
  -> pinned Codecov Action uploads only the aggregate XML, best-effort

regular PMD source-policy job
  -> tools/ci/pmd.sh policy
  -> selected upstream reactor, tests/analyzers not owned here skipped
  -> exact adopted ruleset + XML/HTML integrity + per-rule count ratchet
  -> upload PMD source evidence even when analysis failed late
```

Анализ исходников PMD — принятая регулярная проверка, но она выполняется своей
job CI, отдельно от полного канонического реактора:

```text
make pmd-analysis
  -> tools/ci/pmd.sh policy
  -> ./mvnw -Ppmd-analysis -pl build-support/pmd-report -am verify
       compile the selected upstream reactor; skip tests, JaCoCo and SpotBugs
       run one aggregate-pmd-no-fork execution
       verify exact scope, ruleset, engine, XML/HTML and finding counts

make pmd-watchlist
  -> tools/ci/pmd.sh watchlist
  -> the same lifecycle with a separate three-rule ruleset and output directory
```

Выбор владельца PMD-отчёта и его зависимостей предотвращает конкуренцию этого
агрегатора с независимыми JaCoCo, SpotBugs и CPD aggregate mojos в параллельной
полной сборке. Регулярная политика дополняет отдельный релизный gate
`make verify`. Watchlist запускается локально по выбору и не является merge gate.

`tools/ci/build.sh` и регулярный запуск PMD записывают независимые отпечатки
рабочего дерева. `make context` показывает `verify.fresh` и `pmd.fresh`;
полное локальное заявление о качестве требует обоих результатов `passed` и
свежести для текущих commit и дерева. Watchlist не обновляет свежесть политики PMD.

Наличие workflow и обязательность статуса ветки — разные контракты. Репозиторий
владеет job и артефактами в `.github/workflows/ci.yml`; обязательность для merge
определяется внешними настройками GitHub branch/ruleset и проверяется явно.

Maven может сообщать о необходимости исключительного доступа aggregate mojos
к реактору при параллельной сборке. Это сериализация агрегатной работы Maven,
а не ошибка анализатора. Правильный порядок задают build-support POM: зависимости
определяют production-множество и выполнение агрегации после соответствующих модулей.

## Модель проверок

| Проверка | Вход | Применение |
|---|---|---|
| Maven Enforcer | Toolchain и метаданные POM | Нарушения блокируют обычную сборку |
| Контракты JUnit/Surefire/Failsafe | Быстрые, интеграционные, архитектурные, golden и документационные suites | Surefire владеет `*Test`, Failsafe — `*IT`; отказы и дрейф жизненного цикла/множества отчётов блокируют `verify` |
| ArchUnit | Скомпилированные production-классы | Нарушение зависимости или границы пакета блокирует `verify` |
| JaCoCo | Данные выполнения тестов и 25 production JAR | Точная целостность множества/отчётов, ограничения регрессии агрегата/модулей и фиксированные минимумы агрегата/domain/application блокируют `verify` |
| Codecov | Проверенный агрегатный XML JaCoCo реактора | Только информационные project/base-relative/patch статусы; ошибка внешней отправки не меняет результат локального gate |
| SpotBugs | Применимый production-байткод | Новые, устаревшие, перемещённые или изменившие метаданные находки блокируют точный ratchet; отказы анализатора/отчётов также блокируют |
| PMD CPD | Применимые versioned production Java-исходники | Каждый дубликат виден; отказ анализатора/области/отчёта или изменение принятого количества групп блокирует `verify` |
| Политика исходников PMD | 22 именованных правила над применимыми production Java-исходниками | Отдельная регулярная job CI; правила вне advisory snapshot имеют нулевой допуск, дрейф количества по правилу блокирует |
| Watchlist исходников PMD | Три отложенных правила над теми же исходниками | Явная локальная команда review; находки диагностические, не регулярный CI gate |
| Maven dependency analysis | Main/test байткод | Рекомендательный отчёт по выбору; вне обычного `verify` |
| Dependency-Check | Разрешённый граф зависимостей и локальная база уязвимостей | Отдельный security workflow вне обычного `verify` |

Политика находки отличается от исправности инструмента. Неисправный анализатор
всегда приводит к отказу. CPD и PMD используют небольшие снимки количеств: они
требуют смыслового review при изменении сигнала, не скрывая прежние вхождения.
SpotBugs строже: у каждой принятой сырой находки есть точная проверенная
идентичность вместо одного количества.

Жизненный цикл описан в [docs/TESTING.md](../../TESTING.md). Surefire владеет
набором быстрых имён, Failsafe — интеграционных. Корневая валидация проверяет
принятую таксономию и исходники; поздняя проверка модуля покрытия подтверждает,
что непересекающиеся множества отчётов покрывают ожидаемые исходники. У внешних
suites остаются явные условия, их пропуски не считаются успешной живой проверкой.

Каталог `build-support/build-quality` намеренно не является Maven-модулем.
Корневая `validate` прямо компилирует Java без сторонних зависимостей, поэтому
ошибки области/baseline обнаруживаются до сборки дочерних проектов. Report-модули
содержат только build POM: их зависимости задают порядок и не становятся
runtime-зависимостями или зависимостями библиотек.

## Точный ratchet находок SpotBugs

SpotBugs использует собственный точный ratchet вместо `spotbugs:check`.
Стандартная цель повторила бы анализ и не владела бы политикой принятия
отдельных вхождений. Текущая схема выполняет один нефильтрованный анализ байткода
каждого применимого модуля и использует результат для контроля и представления.

### Область и наследование

Корневой POM владеет наследуемым анализом production-байткода. Реестр
[spotbugs-scope.tsv](../../../build-support/spotbugs-report/spotbugs-scope.tsv)
даёт каждому проекту корневого реактора ровно один статус:

- `analyzed` — production JAR, обязательны сырые и фильтрованные отчёты.
- `excluded` — production-байткод не анализируется; дочерний модуль явно
  задаёт `<skip>true</skip>` у наследуемого плагина SpotBugs.
- `aggregate` — единственный build-only владелец агрегации и позднего gate.

JAR `ioc-application-tck` исключён явно: его main-классы реализуют тестовые
контракты, а не production-поведение. Корень и другие build-only POM также
явно классифицированы, не пропущены неявно.

Корневая `validate` требует равенства путей реестра и корневого набора
`<modules>`, проверяет artifact ID, packaging, явные skip исключённых модулей
и точное равенство зависимостей порядка агрегатора множеству анализируемых.
Новый модуль не допускается до review его статуса и порядка.

### Один анализ, два представления

Каждый анализируемый модуль создаёт:

| Выход | Смысл |
|---|---|
| `target/spotbugs-raw/spotbugs-raw.xml` | Родное нефильтрованное свидетельство анализатора и блокирующий вход |
| `target/spotbugs/spotbugs.xml` | Фильтрованное машинное представление |
| `target/spotbugs/spotbugs.html` | Фильтрованное представление модуля для чтения |

Агрегатор сохраняет то же разделение в `build-support/spotbugs-report/target/`.
Сырой HTML — удобная точка разбора: `target/spotbugs-raw/spotbugs.html`.

Accepted baseline не передаётся анализатору байткода. Корневая `validate`
создаёт untracked `FindBugsFilter` в
`target/build-quality/spotbugs-accepted-filter.xml`; JDK-only
`SpotBugsReportFilter` применяет фильтр движка к готовому сырому XML без
повторного анализа. Фильтрованный отчёт — только спокойное повседневное
представление; контроль всегда сравнивает родной нефильтрованный XML.

### Контракт принятой находки

[spotbugs-accepted-findings.xml](../../../build-support/spotbugs-report/spotbugs-accepted-findings.xml)
— единственный versioned источник принятия. Для каждой находки записываются:

- Стабильный ID свидетельства и модуль-владелец.
- Тип ошибки, instance hash и номер вхождения.
- Priority, rank и category.
- Точный основной класс, метод или поле и JVM descriptor.
- Путь исходника и смещение байткода, если предоставлены анализатором.
- Disposition, owner, evidence и непустое обоснование.
- Конкретное корневое условие пересмотра.
- Узкий селектор представления: тип ошибки, точный класс и точный метод и/или поле.

Строгое сравнение включает идентичность/метаданные анализатора, вхождение и
смещение байткода. Номер строки — только рекомендательная диагностика:
несвязанное смещение строк не меняет baseline. Находки без позиции байткода
используют остальную точную идентичность класса/члена.

Фильтры SpotBugs не выбирают instance hash. Один узкий селектор представления
может скрывать несколько уже рассмотренных вхождений одного члена. Контроль
сохраняется: каждому сырому вхождению нужна собственная принятая идентичность.
Новое вхождение с известным hash или селектором приводит к отказу как новое.

Условия пересмотра называют внешний инвариант принятия, например контракт
происхождения пути или отказа на границе. Общие фразы о пересмотре при любом
изменении кода/анализатора, неизвестные ссылки, повторные и неиспользуемые
условия отклоняются. Селекторы всего пакета, категории или шаблона также запрещены.

### Ранние и поздние проверки

Корневая `validate`:

1. Компилирует общие верификаторы.
2. Выполняет синтетические матрицы области и baseline.
3. Сверяет реактор, реестры анализаторов и зависимости отчётов.
4. Проверяет схему baseline, идентичность, метаданные и условия пересмотра.
5. Создаёт рабочий фильтр представления.

Поздний `verify` агрегатора требует:

- Один здоровый сырой XML и пару фильтрованных XML/HTML каждого анализируемого модуля.
- Отсутствие отчётов анализатора от исключённых модулей.
- Здоровые сырой и фильтрованный агрегаты.
- Ноль ошибок анализатора и отсутствующих классов.
- Равенство сырого агрегата точному мультимножеству сырых находок модулей.
- Точное равенство принятых идентичностей сырым находкам.
- Ноль видимых находок в фильтрованных представлениях модулей и агрегата.
- Соответствие каждого селектора той сырой находке, которую он объясняет.

Поэтому обычный `make verify` завершается неуспешно при новой находке, stale
acceptance исправленной находки, изменении priority/rank/category или строгой
идентичности, дрейфе версии движка, отсутствии отчёта, видимой фильтрованной
находке, расхождении агрегата, ошибке анализатора или отсутствующих классах.

### Работа с отказом SpotBugs

1. Запустите полный `make verify`. Ошибки области/схемы baseline возникают рано;
   дельта находок и целостность отчётов проверяются конечным агрегатором.
2. Изучите сырой XML модуля и HTML сырого агрегата. Пустой фильтрованный отчёт
   не доказывает безопасность.
3. Предпочитайте исправление обоснованной находки с направленной регрессией.
   Удаление находки без её acceptance намеренно вызывает stale-baseline failure.
4. Если находка доказанно является шумом анализатора или неприменимой общей
   политикой, сразу после неуспешного полного анализа запустите
   `make spotbugs-baseline-proposal`. Команда читает текущие сырые отчёты и
   пишет untracked дельту новых/устаревших идентичностей в `target/build-quality/`.
5. Проверьте предложение и вручную измените versioned accepted-findings XML.
   Добавьте ровно одно принятие с disposition, owner, evidence, обоснованием,
   конкретным условием пересмотра и точным селектором. Не копируйте предложение
   целиком и не редактируйте генерируемый фильтр.
6. Удаляйте устаревшее принятие вместе с исчезновением находки.
7. Повторите полный `make verify` и изучите diff принятого baseline до commit.

Предложение намеренно не принимает находки: оно не заполняет поля человеческого
решения и не меняет versioned baseline. При отсутствии/неисправности сырых
отчётов модулей оно также падает. Запускайте его до направленного Maven:
частичный lifecycle может удалить/заменить лишь часть отчётов реактора.

### Обновление toolchain и анализатора

Версии плагина и движка независимо закреплены в корневом POM. Обновление JDK,
компилятора, плагина или движка — явное событие пересмотра baseline:

1. Выполните чистый полный анализ реактора.
2. Изучите каждое изменение идентичности, вхождения, rank и байткода.
3. Проверьте точку применения workflow filter и представление XML/HTML.
4. Обновите принятые метаданные движка только после смыслового review.
5. Выполните полные отрицательные матрицы и второй полный `verify`.

Команды принятия всего нет. Обновление инструмента не должно механически
превращать новые найденные дефекты в принятые находки.

## PMD CPD

CPD анализирует исходники всего репозитория, а не дублирование каждого модуля
отдельно. [cpd-scope.tsv](../../../build-support/cpd-report/cpd-scope.tsv)
даёт каждому проекту реактора явный статус. Агрегатор владеет положительным
списком применимых versioned `src/main/java` и зависит от модулей для порядка.

Из области исключены тестовые контракты, тесты, сгенерированные Maven-исходники,
build output и vendor/generated trees. Корневая `validate` сверяет реестр,
зависимости порядка и корни исходников. Перед анализом удаляется прежний каталог
отчёта; после требуются структурно корректные XML/HTML и точное равенство путей
файлов XML всем текущим Java-файлам анализируемых корней.

Выходы:

- `build-support/cpd-report/target/cpd/cpd.xml` — машинное свидетельство.
- `build-support/cpd-report/target/cpd/cpd.html` — отчёт для чтения.

Совпадения диагностические. Совпадение требует смыслового review, а не
автоматического рефакторинга: одинаковые токены не доказывают общность знания,
допустимость зависимости или полезность абстракции. Порог и языковые настройки
принадлежат report POM и перед изменением требуют калибровки на репозитории.

Report POM также владеет `ioc.cpd.expectedDuplications`. Поздний верификатор
требует равенства количества XML-групп `duplication` принятому снимку.
Рост и уменьшение останавливают сборку: изучите весь XML/HTML, исправьте
случайное дублирование или обновите единственное значение в том же reviewed
изменении. Обновление после уменьшения не даёт неиспользуемому запасу незаметно
пропустить новый долг.

Это ratchet количества групп, а не утверждение, что любое совпадение — дефект,
и не точный CPD baseline. Новая группа может заменить удалённую при том же
количестве; точные отпечатки токенов создавали бы значимый churn, поскольку
границы групп меняются при правках окружающего кода. Усиливайте идентичность
после свидетельств, что простой ratchet повторно пропускает существенные
изменения. Локальные `CPD-OFF`, исключения классов/пар и генерируемые реестры
принятых копий не входят в контракт.

## Политика исходников PMD и watchlist

Анализ PMD — постоянная смешанная блокирующая/рекомендательная проверка,
отдельная от CPD, несмотря на общий Maven PMD Plugin.
[pmd-scope.tsv](../../../build-support/pmd-report/pmd-scope.tsv) определяет статус
каждого проекта; report POM владеет положительным списком production
`src/main/java` и зависимостями порядка.

Versioned [pmd-ruleset.xml](../../../build-support/pmd-report/pmd-ruleset.xml) —
принятая политика: все 22 правила названы индивидуально. Калиброванные свойства:
`CognitiveComplexity.reportLevel=16` и `ExcessiveParameterList.minimum=13`.
Ссылки на целую категорию, исключения ruleset, suppressions и baseline
идентичностей принятых находок запрещены. Плагин и зависимости движка PMD
закреплены независимо, чтобы обновление не вернулось незаметно к встроенной версии.

Пороги `16/13` выбраны после разбора сложных обработчиков и конструкторов.
Более низкие пороги также отмечали плоскую валидацию, обработку состояний и
связывание компонентов фреймворка; ни один проверенный порог
`CyclomaticComplexity` не выделял полезное подмножество. При пересмотре нужна
оценка полезных находок и шума во всей области производственного кода, а не
подгонка под целевое число находок.

Отдельный
[pmd-watchlist-ruleset.xml](../../../build-support/pmd-report/pmd-watchlist-ruleset.xml)
содержит ровно `PreserveStackTrace`, `CloseResource` и `NcssCount`.
Первые два сейчас преимущественно отмечают невидимое PMD владение
фреймворком/жизненным циклом; третий выделяет большие методы для явного review.
Исполнимость сохраняет возможность обнаружения в будущем без заявления,
что нынешний сигнал достаточно качественен для принятия.

Статус правила относится к регулярному выполнению, а не к наличию находок
в день принятия:

| Статус | Смысл | Текущие правила вне принятого набора |
|---|---|---|
| Adopted | Каждая job политики PMD. Правило вне advisory snapshot имеет ожидаемый ноль и блокирует с первого вхождения | 22 точные ссылки в `pmd-ruleset.xml` |
| Watchlist | Исполнимы с полной целостностью области/отчёта, но вне регулярной политики CI | `PreserveStackTrace`, `CloseResource`, `NcssCount` |
| Dropped | Вне регулярного выполнения из-за показанных репозиторием стиля, шума фреймворка/машин состояний или неизмеренного совета об оптимизации | `UseTryWithResources`, `CyclomaticComplexity`, `AvoidDeeplyNestedIfStmts`, `AvoidInstantiatingObjectsInLoops`, `ConsecutiveAppendsShouldReuse`, `ConsecutiveLiteralAppends`, `AddEmptyString` |
| Replaced | Удалённые устаревшие имена PMD 7; поддерживаемый преемник уже принят | `AvoidLosingExceptionInformation`, `UselessOperationOnImmutable` → `UselessPureMethodCall` |

Dropped не означает вечный запрет или принятие прежних находок. Пересмотрите
семейство после major/minor обновления PMD с изменившейся семантикой, доказанного
пропущенного дефекта, существенно нового фреймворка/жизненного цикла, измеренного
долга allocation/string performance или пересмотра релизной политики качества.
Начните с report-only над всей production-областью, а не прямого добавления
в принятый набор.

Профиль выполняет один `aggregate-pmd-no-fork` в `verify`, предварительно
удаляя только выбранный старый вывод PMD. Политика пишет:

- `build-support/pmd-report/target/pmd/pmd.xml` — машинные находки.
- `build-support/pmd-report/target/pmd/pmd.html` — отчёт для чтения.

Watchlist сохраняет такую же пару в `target/pmd-watchlist/`, не перезаписывая
и не подтверждая случайно отчёт принятой политики.

[pmd-advisory-counts.tsv](../../../build-support/pmd-report/pmd-advisory-counts.tsv)
— полный ненулевой снимок PMD. Каждая строка называет точное принятое правило,
ожидаемое количество и причину рекомендательного статуса сигнала.
Для отсутствующих принятых правил ожидается ноль. Требуется точное равенство
по правилу: и рост, и улучшение требуют смыслового review и явного обновления.
Это не suppression: все вхождения видны в XML/HTML, правило вне принятого
ruleset в снимке отклоняется.

Это ratchet количеств, а не baseline идентичностей. Удаление одной находки
и добавление другой того же правила сохраняет количество. Полный XML/HTML
остаётся свидетельством review этого остаточного риска; baseline положения/
отпечатка PMD стоит добавлять, только если повторные пропуски оправдывают
затраты сопровождения.

Верификатор целостности сверяет реактор, реестр, зависимости отчёта, корни
исходников, UTF-8, зависимости движка и точный ruleset. Затем требует оба отчёта,
отклоняет ошибки обработки/настройки PMD и файлы вне текущего множества исходников.
XML PMD содержит только файлы с находками; файл без находок покрывается
положительным списком корней/исходников, а не выдуманной строкой отчёта.

Корневая валидация закрепляет оба точных rulesets, калиброванные свойства,
выбор профиля, удаление старого вывода и позднюю команду проверки с
`failonerror=true`. Неожиданная настройка правила, source include/exclude и
production-маркеры `NOPMD` или `@SuppressWarnings("PMD…")` отклоняются.
Удаление gate или локальное suppression не делают находки невидимыми.
Поздняя проверка также отклоняет правило, не входящее в выбранную политику/
watchlist: пути отчётов нельзя незаметно подменить. Затем политика сверяет все
количества; количества watchlist не ограничиваются.

Новая находка нулевого допуска или дрейф advisory count завершают
`make pmd-analysis` неуспешно. Регулярная job CI вызывает ту же leaf-команду
репозитория и сохраняет полный XML/HTML. Обычный `make verify` не активирует
профиль из-за прежней конкуренции выбранного агрегатора с независимыми
aggregate mojos в параллельном полном реакторе.

Не добавляйте `pmd:check`, `NOPMD`, аннотации, исключения или baseline
идентичности ради успешного отчёта. Смыслово проверьте каждое изменившееся
вхождение: исправьте, когда уместно; иначе обновите соответствующее ненулевое
количество и обоснование в том же reviewed изменении. Перенос правила в
watchlist требует свидетельств и reviewed изменения политики, это не suppression.

Запускайте `make pmd-watchlist` при изменении следующих предпосылок:

- Преобразование исключений, причинная цепочка или приоритет вторичного отказа.
- Передача владения JDBC, SMB, Spring context, executor и другими closeable lifecycles.
- Существенная перестройка большого метода/типа или появление нового.
- Движок PMD, Maven PMD Plugin, JDK или уровень языка исходников.
- Перед предложением принять любое правило watchlist.

Watchlist остаётся рекомендательным и вне регулярного CI. Результат всё равно
должен быть структурно здоровым: отсутствие отчётов, ошибка анализатора,
дрейф области или ruleset приводят к отказу команды.

## Покрытие

[TESTING.md](../../TESTING.md#coverage-quality-gate) владеет политикой покрытия/
качества тестов, включая фиксированные минимумы и добавление полезных
поведенческих проверок. Здесь описаны сбор, источник истины и применение.

### Сбор и авторитетность отчётов

Наследуемый агент JaCoCo добавляет выполнение Surefire и Failsafe в
`target/jacoco.exec` каждого функционального модуля. При включённых тестах
`initialize` удаляет старые результаты, данные выполнения и каталоги покрытия
модулей/агрегата. Packaging/analyzer с пропущенными тестами сохраняет прежние
свидетельства и не обновляет покрытие.

Локальные XML/HTML формируются в `target/site/jacoco/` во время `verify`
модуля. Последующий build-only модуль объединяет данные production-графа в
`build-support/coverage-report/target/site/jacoco-aggregate/`.
Группа агрегата может учитывать последующее интеграционное/E2E выполнение,
которого ещё не видел ранний локальный отчёт. Gate использует счётчики агрегата/
групп; локальные отчёты обязательны для исследования/целостности и не являются
вторым источником baseline. Доли реактора вычисляются по суммам счётчиков,
а не среднему процентов модулей.

### Реестры области и политики

| Реестр | Ответственность |
|---|---|
| [coverage-scope.tsv](../../../build-support/coverage-report/coverage-scope.tsv) | Статус каждого проекта реактора и required/aggregate-only/отсутствующий локальный отчёт |
| [coverage-ratchets.tsv](../../../build-support/coverage-report/coverage-ratchets.tsv) | Точные baseline-счётчики строк/ветвей, пропущенные инструкции, явная политика инструкций и обоснование |
| [coverage-floors.tsv](../../../build-support/coverage-report/coverage-floors.tsv) | Фиксированные минимумы строк/ветвей либо явный `none` для ratchet-only |

Сейчас область включает 31 проект, 25 production-групп и 24 обязательных
локальных отчёта. Корень, переиспользуемый TCK и build-only POM находятся вне
production-знаменателей; `ioc-platform-errors` — aggregate-only без собственного
тестового JVM. Выполнение из зависимых модулей всё равно входит в агрегат.
Ручные includes/excludes классов/пакетов JaCoCo и skip override покрываемого
модуля отклоняются.

Корневая `validate` компилирует JDK-only `CoverageVerifier`, выполняет
синтетическую матрицу и сверяет реактор, реестры, координаты артефактов,
зависимости порядка агрегата, наследуемые agent/report/cleanup и поздний gate.
Каждому агрегату/production scope нужны строки ratchet и floor policy.

Поздний `verify` требует непустые XML/HTML агрегата, точный состав групп и суммы
счётчиков плюс ожидаемые локальные XML/HTML и данные выполнения. Неожиданные
локальные данные/отчёты исключённых и aggregate-only областей отклоняются. Очистка старого вывода не
позволяет старому файлу заменить отсутствующий новый в каноническом lifecycle.
Отдельный верификатор тестов проверяет точное множество исходников/Surefire/
Failsafe. Хороший процент не компенсирует нарушение целостности отчётов.

### Точные сравнения

Для реактора и каждой production-группы gate независимо проверяет отсутствие
регрессии строк/ветвей относительно записанной дроби и применимый фиксированный
минимум:

```text
actualCovered * baselineTotal >= baselineCovered * actualTotal
actualCovered * 100 >= minimumPercent * actualTotal
```

Реализация использует целочисленные перекрёстные произведения, поэтому округление
HTML не скрывает регрессию. Ratchet отклоняет новый ненулевой счётчик после
нулевого знаменателя baseline и исчезновение ранее ненулевого; область с
фиксированным минимумом не проходит за счёт отсутствующего знаменателя.

Абсолютное число пропущенных ветвей также не растёт. Например, переход с
80/100 покрытых ветвей на 170/200 улучшает долю с 80% до 85%, но увеличивает
пропуски с 20 до 30 и не проходит проверку абсолютного числа.

Пропущенные инструкции ограничиваются только при `enforced` в столбце
`absolute-instructions`; `observed` сохраняет число для review. Маленькие
области часто используют эту защиту, но решение задаёт явный реестр, а не
автоматически определяемый размер модуля.

### Разбор отказа покрытия

1. Определите вид отказа: топология/целостность отчёта, минимум, доля,
   пропущенные ветви или ограничиваемые инструкции. До изменения тестов
   прочитайте названную область и точные счётчики.
2. При неполных свидетельствах восстановите правильные lifecycle/отчёты и
   выполните полный gate. Направленный запуск или пропуск тестов не заменяет агрегат.
3. При пробеле поведения следуйте
   [порядку работы с покрытием](../../TESTING.md#reach-the-gate-through-useful-tests):
   выберите случай контракта и независимое ожидание на владеющем слое.
4. При правомерном удалении/рефакторинге или новой области/счётчике явно
   проверьте знаменатель, поведение и тесты. Сохраните минимумы; не снижайте
   baseline, не меняйте тип отчёта и не добавляйте исключения ради прохода.
5. После направленных проверок выполните полный gate. Принимайте устойчивые
   улучшения с точными счётчиками/обоснованием в том же reviewed изменении;
   изучайте защищённые метрики вместе, чтобы одна правка не ослабила другую.

### Передача в Codecov

После успешной сборки CI `tools/ci/codecov.sh verify-input` повторяет локальную
проверку отчётов/политики до сохранения. Отдельная job скачивает свидетельство,
требует XML агрегата и запускает Codecov Action с полным закреплённым SHA и
закреплённый CLI для отправки только явного файла. Поиск отчётов, плагины и
телеметрия отключены; OIDC принадлежит job отчётности.

Project/base/patch статусы Codecov информационные. Отсутствующее проектное
свидетельство приводит к отказу своей проверки; только внешний Action работает
по возможности. Внешний отказ не заменяет локальный контроль и не превращает
неуспешное покрытие в успешное. Точные цели отчётности определены в
[TESTING.md](../../TESTING.md#codecov-reporting).

## Анализ зависимостей и безопасности

`make dependency-analysis` собирает main/test байткод без выполнения тестов,
затем последовательно запускает Maven Dependency Plugin. Не заменяйте
`-DskipTests` на `-Dmaven.test.skip=true`: второе отключает компиляцию тестов
и меняет анализируемое множество.

Находки рекомендательные: анализ байткода не полностью моделирует starters,
SPI/ServiceLoader, runtime-реализации и общие тестовые агрегаты. Профиль
`dependency-analysis` по выбору выполняет тот же анализ внутри полного
`verify`; ни один вариант не входит в обычный CI, общего широкого ignore
реестра нет.

OWASP Dependency-Check — отдельная проверка безопасности. Сетевые обновления
базы явные, обычное локальное сканирование использует имеющиеся данные.
Lifecycle и suppressions принадлежат security workflow, а не принятию
качества кода SpotBugs/CPD.

## Добавление или изменение Maven-модуля

1. Добавьте/измените модуль корневого реактора с сохранением направления зависимостей.
2. Явно определите его статусы coverage, SpotBugs, CPD и PMD. Различия требуют
   обоснования; ни один реестр не пропускает проект незаметно.
3. Добавьте зависимости порядка отчётов и точные production-корни CPD/PMD.
   Проверьте локальный отчёт покрытия, группу агрегата, измеренный ratchet и
   floor entry, включая явный `none`, когда применимо.
4. Для исключённого SpotBugs-модуля явно задайте наследуемый `skip=true`.
   Проверьте добавленные/удалённые/переклассифицированные suites и реестр исходников.
5. Выполните направленные тесты, затем полный `make verify` и `make pmd-analysis`;
   вместе изучите состав отчётов, находки и дельты счётчиков/baseline.
6. Используйте `make ci`/`make pre-push` для полного обычного локального gate.
   Свежие свидетельства требуют `verify.fresh=true` и `pmd.fresh=true`.
7. Обновите затронутые документы возможностей, карту модулей и локальный README
   при изменении ответственности или production/test/build-only классификации.

Не обходите отказ нового модуля ослаблением равенства реестра или проверки
отчётов. Обязательный статус предотвращает незаметную потерю области анализатора.

## Развитие системы качества

Новый анализатор начинается с измеренного отчёта, а не немедленного
блокирующего gate. Сначала определите сигнал, множество исходников/байткода,
отказы здоровья инструмента, воспроизводимые машинные/читаемые отчёты,
владение, стоимость и решения по сигналу/шуму. До принятия обеспечьте:

- Один авторитетный реестр области или другое fail-closed получение.
- Удаление старого вывода и обнаружение отсутствующего отчёта.
- Детерминированный агрегат для межмодульных свидетельств.
- Фикстуры дрейфа области и отрицательных путей отказа.
- Узкую проверяемую семантику принятия, если нужен baseline.
- Один обычный путь Maven lifecycle, общий для локальной сборки и CI.

Не используйте принятие SpotBugs как общий механизм suppressions: у инструментов
различаются идентичность, шум и отказы.

## Граница ресурсных свидетельств

Операционные smoke/load Native остаются инструментами разработки по выбору
и не заменяют детерминированный gate или подготовленные внешние транспортные
тесты. Реализация, исторические измерения и ограничения описаны в
[native capacity](../native-capacity.md). Закрытые экспериментальные драйверы и
временные релизные комплекты не входят в поддерживаемый lifecycle качества.

## Когда обновлять документ

Обновляйте документ в том же изменении при смене:

- Канонического Maven lifecycle локальной сборки/CI или порядка report-модулей.
- Классификации области анализатора или допуска нового модуля.
- Владельца контроля сырого и фильтрованного представления.
- Идентичности принятой находки, условия review или безопасности proposal.
- Политики отказа анализатора/отчёта или блокирующего/диагностического статуса.
- Формата/порядка обновления снимков количеств PMD/CPD.
- Путей агрегатов/отчётов для разработчика или CI.
- Множества покрытия, порогов или принятия dependency analysis.

Не обновляйте документ ради patch-версии инструмента, количества находок,
длительности отчёта или отдельного принятия без изменения механики.

## Координаты библиотек и допуск публикации

Верификаторы допускают `io.github.xorex-lc` для шести артефактов
[каталога библиотек](../../guides/libraries/README.md): concurrency, diagnostics
API, SLF4J logging, configuration inspection, events core и Spring adapter.
Остальные JAR реактора сохраняют `com.iocextractor`. Отрицательные фикстуры
отклоняют чужие координаты и старую группу принятых библиотек.

Выделение или публикация библиотеки не исключает её runtime-байткод из покрытия
или статического анализа. Все четыре реестра, зависимости отчётов, корни
исходников и требования локальных отчётов остаются согласованными. Явная
классификация тестовой поддержки TCK — другая причина исключения.

Допуск публикации — отдельный контракт: независимый от родителя consumer POM,
зависимости конкретного компонента, байты main/sources/Javadoc/license, подписи,
неизменяемые комплекты и восстановление.
[Инструменты публикации](../../../tools/ci/library-publication.py) владеют точными
правилами артефактов/зависимостей; [руководство](../../guides/library-publication.md)
— использованием, [политика релизов](../../RELEASE-PROCESS.md#reusable-library-versions)
— версиями/допуском.

Компонентная матрица CI квалифицирует concurrency, diagnostics, logging и
configuration. Отдельная events job квалифицирует core перед Spring adapter;
агрегатный статус `library-consumer` успешен только при успехе обеих job.
Failed, cancelled и skipped job не дают успешный агрегат. Обязательность
статуса определяется внешними настройками branch/ruleset.

Отдельные потребители используют изолированные settings/cache вне checkout,
проверяют байты manifest/выбранное происхождение и выполняют реальные примеры
руководств. Boot-рецепты приложения остаются интеграционными тестами bootstrap;
Boot находится вне общего logging JAR. Инструментальные фикстуры не добавляют
suites реактора или production-групп. Успех локального file-репозитория не
доказывает публичную публикацию или второй развёрнутый сервис.
