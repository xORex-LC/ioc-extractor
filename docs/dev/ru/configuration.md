# Конфигурация и граница запуска

[English version](../configuration.md)

Дерево `ioc.*` — строгий внешний контракт приложения. Bootstrap связывает его с
`IocProperties`, отклоняет неизвестные объявления и несовместимые значения,
затем собирает рабочий граф. Доменный и прикладной код получают собственные
значения и порты; они не читают свойства Spring и переменные окружения.

[Операторский справочник](../../guides/ru/configuration.md) описывает имена
параметров, значения по умолчанию и применение изменений. Этот документ
описывает ход проверки, распределение ответственности между сервисом и
библиотекой и границу между проверкой настроек и началом работы.

## Источники и приоритеты

Для обычных поддерживаемых источников приоритет растёт слева направо:

```text
classpath application.yml < external YAML < environment < JVM system properties < CLI
```

Конфигурация из classpath импортирует необязательный `./configs/application.yml`.
Установленный unit добавляет `./etc/application.yml` относительно каталога
установки. Boot также разрешает импорты, документы и файлы активных профилей и
`SPRING_APPLICATION_JSON`; приведённый порядок не перечисляет все источники
Boot. JSON имеет преимущество перед обычными переменными окружения и свойствами
JVM, а аргументы CLI сохраняют высший приоритет. При сравнении проверки с
работающей установкой нужно явно учитывать правила загрузки источников.

Список целиком заменяется источником с наибольшим приоритетом, который задаёт
этот список. Объявление только `ioc.refang.rules[0].from` теряет исходное поле
`to` и все правила из менее приоритетных источников; неполный элемент отклоняется.
Задавайте все обязательные поля всех сохраняемых элементов. Для словарей записи
объединяются, а значение одинакового ключа берётся из более приоритетного
источника. Поведение элементов списка нельзя переносить на словари.

Префикс `IOC_*` зарезервирован для настроек IOC. `IocEnvironmentPropertyMatcher`
сопоставляет имена с разделителями-подчёркиваниями с объявленной структурой
записей, включая индексы списков. Неизвестные имена отклоняются; неоднозначное
разбиение не угадывается. IOC сохраняет собственные правила написания и
совместимости преобразователей поверх
[общей инспекции объявлений](../configuration-inspection.md). Более широкое
распознавание имён библиотекой не расширяет синтаксис сервиса.
Неперечислимые пользовательские источники требуют отдельной проверки полноты;
добавление `PropertySource` само по себе не доказывает проверку всех имён.

После обновления контекста и до запуска runners
`IocConfigurationOverrideReporter` один раз сообщает `ioc.key <- source` для
первого внешнего объявления каждого имени. Значения он не читает. Это
происхождение объявления, а не доказательство значения, использованного Binder:
затенённые элементы списков и объявления null могут оставаться наблюдаемыми.
Отчёт принадлежит обычному запуску; минимальный контекст проверки не сканирует
этот компонент.

## Ход проверки и ответственность

```text
Boot ConfigData loading (YAML, imports, profiles, effective overrides)
  -> unknown-name preflight over prepared sources
  -> typed binding and conversion
  -> Bean Validation and collect-all IOC semantic validation
  -> registry references, artifact policies and named-plan admission
  -> runtime composition and state-dependent checks
  -> startup recovery / readiness / operational work
```

| Компонент | Ответственность |
|---|---|
| `IocProperties`, `IocProcessingProperties` и преобразователи селекторов | Внешняя структура, преобразование типов, обязательные значения и локальные ограничения |
| `IocUnknownConfigurationPreflight` | Неизвестные имена в поддерживаемых YAML, CLI, свойствах JVM и окружении, включая затенённые объявления |
| `IocConfigPreflight` | Межсекционные ограничения: жизненный цикл, бюджеты исполнения, идентичность артефактов, формат CSV, ссылки синхронизации и каталог импорта |
| `ConfigRegistryPreflight` и соответствующие каталоги | Зарегистрированные поставщики/преобразования/фильтры/предикаты, политики записи, именованные планы и привязки обработки импорта |
| `AppConfig` и остальные конфигурации рабочего графа | Конкретные адаптеры, планы экспорта, миграции хранилищ, совместимость сохранённой политики, восстановление и планировщики |
| Проекция ошибок и анализаторы | Выбранные категории, безопасные пути полей и рекомендации; см. [отчёты об ошибках](configuration-failure-reports.md) |

Конструкторы не должны бросать исключения для обычных ошибок оператора,
подлежащих совместной проверке. Иначе преобразование остановится на первой
ошибке и скроет остальные нарушения. Сбор всех ошибок действует внутри
достигнутой фазы; ошибка синтаксиса или преобразования не подтверждает выполнение
последующих проверок.

Выключатель рабочего механизма не делает произвольные объявления неактивными.
Неизвестные имена и объявленные ссылки на реестры и планы всё равно проверяются.
Контракт импорта `processed` требует именованный маршрут даже при отключённом
приёме. Некорректный подготовленный каталог не должен ждать первой доставки,
чтобы обнаружить ошибку.

## Команды проверки конфигурации

`IocExtractorApplication` обрабатывает внутренние точки входа упаковки до
обычного CLI и рабочего контекста Spring:

| Точка входа | Область и результат |
|---|---|
| `--ioc.validate-yaml=<file>` / `IocYamlSyntaxCheck` | Только чтение и разбор файла; `CONFIG.YAML_VALID` и код `0` не подтверждают привязку и семантическую корректность |
| `--ioc.validate-config=<file>` / `IocSemanticConfigurationCheck` | Синтаксическая проверка и минимальный контекст настроек; `CONFIG.SEMANTIC_VALID` и код `0` подтверждают реализованные предварительные проверки конфигурации |
| Установленный `ioc-config check [candidate.yml]` | Создаёт доступную сервису копию YAML и вызывает семантическую проверку от его учётной записи; без candidate проверяется установленный YAML |

Ошибки checker возвращают `78`. Ошибки вызова, чтения и незавершённые проверки
остаются отказом; их коды различает [контракт отчётов](configuration-failure-reports.md).
Успешная проверка не открывает рабочие SQLite-хранилища, не создаёт транспортные
соединения и не запускает приём или планировщики. Она также не квалифицирует
права файловой системы, удалённые узлы, схемы существующих БД, сохранённую политику
жизненного цикла и восстановление по фактическому состоянию. Проверки только
рабочего графа, например исполнимости плана экспорта, не входят автоматически в
`CONFIG.SEMANTIC_VALID`.

### Эффективные источники и защита контекста

Семантическая проверка явно загружает значения classpath и candidate.
Разрешённые импорты Boot, профили и внешние переопределения продолжают участвовать;
существующий `./configs/application.yml` подключается через импорт classpath.
Отсутствующий обязательный импорт вызывает отказ; необязательный может
отсутствовать. Проверяется эффективная конфигурация, а не изолированный файл.

Checker отклоняет управление через CLI свойствами `spring.config.location`,
`spring.config.additional-location`, `spring.config.import` и
`spring.config.name`, включая индексные и альтернативные формы. Объявления
`spring.main.sources` и индексные потомки отклоняются во всех загруженных
каналах до создания бинов дополнительных источников. Собственные настройки
проверки принудительно задают невебовый контекст и немедленную проверку без
keep-alive, регистрации shutdown hook и вывода сведений о запуске. После проверки
контекст закрывается.

Импорты — доверенный вход установки; минимальный граф бинов не ограничивает
пути, сетевой доступ или загрузчики конфигурации. Подавление консоли временно
меняет потоки процесса под монитором checker; произвольные appenders находятся
вне этой границы. Это короткоживущая команда, а не встраиваемый обработчик общего
процесса. [Отдельный библиотечный пример](../../guides/ru/libraries/config-spring-boot-check.md)
показывает другую политику источников: явный YAML и буквальные переопределения
без внешнего окружения, импортов ConfigData и профилей. Общий инспектор не
навязывает политику ни одного сервиса.

## Установленные check, apply и запуск

Помощник `ioc-config` работает через systemd с учётной записью сервиса, рабочим
каталогом, EnvironmentFile и параметрами JVM. Подготовленная копия сохраняет
расширение YAML и доступна для чтения сервису. `check` не перезапускает сервис.
`apply` требует отдельный обычный файл без символьной ссылки, исключает
одновременные применения, подготавливает и проверяет байты, затем атомарно
заменяет рабочий YAML и перезапускает сервис с ограниченным ожиданием health.

Отказ предварительной проверки сохраняет рабочий YAML и сервис без изменений.
Неуспешный перезапуск или ожидание health сохраняет отклонённый YAML,
восстанавливает предыдущий файл и повторяет перезапуск и проверку health.
Восстановленные байты не подтверждают здоровье прежнего сервиса. Это
восстановление файла настроек: оно не отменяет миграции БД, активацию жизненного
цикла, принятую работу и удалённые эффекты. Настройки, меняющие состояние,
требуют соответствующей процедуры миграции и резервного копирования до apply.

`ExecCondition` установленного unit повторяет семантическую проверку до основной
активации. Код `78` пропускает активацию без перехода в `Restart=on-failure`;
`RestartPreventExitStatus=78` дополнительно защищает основной процесс. Локальное
развёртывание проверяет подготовленный новый JAR с окружением сервиса до остановки
активного сервиса и начала резервного копирования и активации. Проверки общие,
области восстановления различаются; процедуры описаны в
[документации упаковки](../../../packaging/README.md).

Общей горячей перезагрузки нет. Поддерживаемый способ изменения YAML — помощник
с отдельным candidate; изменение файла окружения требует перезапуска. Синтаксис
systemd EnvironmentFile отличается от shell; загружать его через `source` нельзя.

## Режимы работы и ленивая инициализация

`ioc.runtime.mode` выбирает `oneshot` или `daemon`; режим наблюдаемости выбирает
логирование и не заменяет режим исполнения. Обычные лёгкие пути справки, версии,
синтаксических ошибок и HTTP-клиента health могут завершиться до запуска Spring.
Эти пути не проверяют конфигурацию приложения. Явные аргументы daemon выбирают
рабочий путь вместо обычного раннего выхода CLI. Версия требует встроенной
идентичности сборки; при отсутствии метаданных возвращаются однострочная ошибка
и код `1`, без выдуманной версии.

Oneshot использует ленивую сборку рабочего графа, сохраняя немедленную проверку
конфигурации. Daemon принудительно создаёт singleton-бины сразу и включает
веб-интерфейс actuator. Миграции и согласованное восстановление предшествуют
приёму; успешная проверка конфигурации не подтверждает прохождение этого барьера.
Конкретные адаптеры остаются в `AppConfig`, `SyncConfig`,
`EventCoordinationConfig` и соответствующих конфигурационных классах bootstrap.

## Настройки, связанные с сохранённым состоянием

- **Жизненный цикл:** classpath использует `disabled`; свежий production template
  задаёт `fixed/12h` и `existing-records: reject`. Существующая установка сохраняет
  YAML оператора. Разрушительная обработка старых строк требует явного `expire`;
  после начала сохранённой активации возврат этой БД в `disabled` завершается
  `LIFECYCLE.POLICY_MISMATCH`. Ноль не является командой очистки. См.
  [внутреннее устройство](../canonical-record-lifecycle.md) и
  [операторскую процедуру](../../guides/ru/canonical-record-lifecycle.md).
- **Управляемый импорт:** обе поставляемые конфигурации отключают приём.
  Каталоги classpath пусты; production template уже объявляет полномочия и
  processed-контракт агрегата с соответствующим планом, но без источников.
  Включение требует режима daemon, JDBC-хранилищ, фиксированного срока действия
  и полного принятого каталога источников, полномочий и контрактов. Компиляция
  создаёт один неизменяемый результат с отпечатком поведения; частично
  разрешённого рабочего каталога нет. Импорт и обычный ingest разделяют барьер
  восстановления при запуске. Источники SMB используют endpoints даже при
  отключённой обычной синхронизации; polling остаётся основой корректности,
  приватные каталоги SMB и права подготавливает оператор. Снимки остаются
  локальными и независимыми от транспорта. См. [механику импорта](../dataframe-import.md).
- **Обработка и допуск:** соотношения бюджетов проверяются совместно;
  подготовительные потоки и ограниченное окно не делают каноническую запись
  параллельной. Смена выбранной политики может блокировать восстановление
  незаконченной работы; следуйте [процедуре завершения очереди](../../guides/ioc-processing-routes.md).
- **Идентичность:** ключи записи/сопоставления и epoch именуют сохраняемые
  контракты. Правка YAML не мигрирует идентичность заполненного хранилища.
  В поддерживаемом окне отката к v0.2.0 `V020ArtifactIdentityCompatibility`
  принимает только четыре точных старых встроенных определения. Полный старый
  набор также разрешает поставляемую идентичность агрегата при наличии его sink.
  Изменённые и пользовательские похожие определения отклоняются.
  `CONFIG.LEGACY_ARTIFACT_IDENTITY` не содержит значений; адаптер удаляется после
  исключения старого бинаря из поддерживаемого пути отката.
- **Переименования:** ограниченная политика alias определена
  [ADR 0027](../../ADR/0027-rollback-safe-configuration-evolution.md). Временный
  типизированный alias `smb.encrypt` отсутствует в свежих шаблонах и наблюдается
  через `IocConfigurationMigrationCatalog`. Семантическая проверка после binding
  отклоняет одновременные старое и новое поля; преобразование Boolean и срок
  удаления принадлежат IOC. Удалённый `read-timeout` остаётся неизвестным и
  получает `CONFIG.LEGACY_SYNC_TIMEOUT`, без восстановления поля-заглушки.

## Расширение и проверка

Новый параметр требует обновления типизированной структуры, значений по умолчанию
и семантики отсутствия, валидации, метаданных, полного production template и обеих
версий справочника. Добавьте проверки binding и существенных отказов и границ.
Селекторы используют типизированные значения и преобразователи. Поставщик,
преобразование или предикат регистрируется в каталоге, общем для предварительной
проверки и сборки. Новые каналы сохраняют строгие имена, полноту инспекции и
контролируемый вывод; обходить `Environment` нельзя.

Обновлять при изменении выбора источников, приоритетов, поведения списков и
словарей, владения проверками, гарантий checker, правил alias или границ
рабочего запуска и восстановления.
