# ADR 0029: Публикация из release-ветки с компонентными тегами

Статус: принято, 2026-09-08.

<a id="context"></a>
## Контекст

ADR 0028 изначально требовал для concurrency-библиотеки продуктовый тег `vX.Y.Z`,
выбранный из default branch. Default branch остаётся на последнем завершённом
релизе продукта, пока следующий собирается в ветке `release-X.Y.Z`. Перенос
незавершённого кода приложения в default branch только ради публикации
библиотеки нарушил бы эту модель. Продуктовый тег также запустил бы существующий
workflow выпуска приложения.

GitHub обнаруживает и разрешает ручной запуск `workflow_dispatch` только при
наличии файла workflow в default branch. После регистрации там maintainer
может выбрать другую ветку для запуска. Поэтому копия для обнаружения в default
branch и source commit, допущенный к публикации, — разные вопросы.

Владелец также рассмотрел независимые версии библиотек. Сейчас нет потребителя
или периодичности выпуска, которые оправдывали бы эту операционную стоимость.

<a id="decision"></a>
## Решение

Этот ADR заменяет только выбор default branch и продуктового тега из ADR 0028.
Concurrency-библиотека пока сохраняет продуктовую линию версий. Релиз продукта
`X.Y.Z` и его concurrency-артефакт используют версию `X.Y.Z`; RC использует
соответствующую `X.Y.Z-rc.N`. Будущий ADR может ввести независимую версию
библиотеки, когда реальные потребители потребуют выпусков вне продуктового ритма.

Публикация библиотеки использует аннотированный компонентный тег:
`ioc-platform-concurrency-vX.Y.Z` или `ioc-platform-concurrency-vX.Y.Z-rc.N`.
Он не соответствует триггеру выпуска приложения `v*`. Workflow запускается
для соответствующей ветки `release-X.Y.Z`. Допуск требует выполнения всех условий:

- выбранный ref — именно ветка `release-X.Y.Z`;
- компонентный тег аннотирован, его версия соответствует этой ветке;
- тег разрешается в commit, содержащийся в выбранной release-ветке;
- сборка, подпись и публикация работают с этим разрешённым commit;
- восстановление использует те же tag, release branch, подписанный bundle и
  identity deployment Central.

Файл publication workflow также существует в default branch, чтобы GitHub мог
зарегистрировать `workflow_dispatch`. Выбор default branch или development-ветки
завершает admission ошибкой до подписи или доступа к репозиториям. Это добавление
операционного workflow не сливает незавершённый код приложения в default branch.

<a id="consequences"></a>
## Последствия

Библиотеку можно подготовить и опубликовать, пока релиз продукта остаётся в
release-ветке. Публикация компонента и выпуск приложения запускаются независимо,
а номера версий остаются согласованными. Maintainer должен создать и сохранить
аннотированный компонентный тег и явно выбрать соответствующую release-ветку.

Default branch содержит publication automation, которая может быть новее кода
приложения в ней. После admission неизменяемый компонентный тег остаётся
источником сборки и привилегированных publication scripts. Требования ADR 0028
к публикации в репозиториях и независимому потреблению не меняются.
