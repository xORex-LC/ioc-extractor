<a id="adr-0030-registered-observation-order-for-mutable-artifact-fields"></a>
# ADR 0030: Зарегистрированный порядок наблюдений для изменяемых полей артефактов

Статус: принято, 2026-09-26. Реализовано и квалифицировано для 0.3.0.

<a id="context"></a>
## Контекст

Канонические строки сейчас используют keep-first insertion. Новый IOC aggregate
имеет одно `name` на четырёхполевой IOC-ключ, и более поздняя доставка с непустым
именем должна заменять более раннюю даже при обратном порядке завершения обработки.
Обработка документов, managed import и oneshot используют общую dataframe DB,
но их delivery ledgers имеют отдельные правила последовательности и восстановления.
Демон поддерживает как файловый ledger, так и JDBC service ledger.

<a id="decision"></a>
## Решение

Dataframe DB владеет версионируемым монотонным порядком admission и случайным
идентификатором namespace. Регистрация индексируется стабильным ID отдельного
случая доставки. Повторная регистрация того же случая возвращает его исходный
порядок; возобновление отсутствующей регистрации завершается ошибкой. Ни время,
ни content hash, имя файла, завершение worker или sequence service ledger
не определяют приоритет поля.

Service ledger владеет резервированием документа, claim и восстановлением.
Его JDBC- и файловая реализации удовлетворяют одному journal-контракту. Journal
сохраняет резервирование до регистрации, затем сохраняет возвращённую ссылку до
claim приватного файла с token в имени. Восстановление принимает этот файл либо
отказывает при противоречивых evidence. Managed import использует durable delivery
ID после claim reservation; oneshot использует invocation ID и оставляет
регистрацию после сбоя неразрешённой для явной operator reconciliation. Dry-run
не регистрируется.

Политика поля сравнивает `(admission order, occurrence position)` внутри активного
канонического lifecycle. Более новое непустое значение может заменить старое;
то же значение продвигает provenance, не меняя публичную строку. Пустые значения
сохраняют записанное значение и origin. Одинаковый ранг с конфликтующими evidence
завершается ошибкой. Изменение публичного имени продвигает обычную projection и
export revision; изменение только provenance — нет. Поле и его provenance
коммитятся атомарно в dataframe DB после существующего failure-policy checkpoint.
Транзакции, охватывающей service и dataframe DB, нет.

Первоначальный aggregate отображает ровно один наблюдаемый носитель в каждую
строку. Его полный четырёхполевой кортеж без имени является и record identity,
и match identity. Политика настраивается для каждого artifact/field и не меняет
keep-first поведение существующих артефактов. Корреляция нескольких носителей
ожидает явного входного контракта.

<a id="producer-and-recovery-contract"></a>
## Контракт producer и восстановления

Локальные producer публикуют полный закрытый файл атомарным rename в inbox и
никогда не пишут в него после публикации. Quiet period потребителя — подсказка
для latency/stability, а не доказательство неизменяемости. До registered claim
нужно захватить доступную file identity и metadata; выполнить claim в приватный
token path; хешировать принадлежащие consumer байты и перепроверить
identity/size/mtime до допуска к обработке. При изменении доступной identity,
замене файла по тому же пути или изменении содержимого во время хеширования —
quarantine/fail closed. Если filesystem не даёт достаточной identity,
заменой может быть только принадлежащий consumer неизменяемый snapshot,
захваченный до регистрации, с проверкой digest перед обработкой. Адаптер,
не способный дать ни надёжную identity, ни такой snapshot, отказывает закрыто;
он никогда не назначает заменившим байтам более раннюю регистрацию. Полная
матрица P0 включает замену с теми же size/mtime и открытый writer, переживший
rename. Нарушивший handoff-контракт producer не может требовать упорядоченной
обработки только на основании наблюдения quiet period.

<a id="consequences"></a>
## Последствия

Регистрация в dataframe может оставлять безвредные пропуски порядка после
отклонённой доставки. Journal и terminal handshake сохраняют recovery evidence,
пока оба store не согласованы; cleanup не должен превращать старый retry в новую
регистрацию. Восстановленная service DB в паре с другим dataframe namespace
отказывает до IOC mutation. Существующая unranked работа должна завершиться до
активации политики. Rollback после миграции схемы требует согласованного
pre-upgrade restore; downgrade только бинаря не поддерживается. Это операционное
ограничение, а также aggregate export profile/default activation остаются
релизными решениями.
