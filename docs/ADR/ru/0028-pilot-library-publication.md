<a id="adr-0028-publish-the-concurrency-pilot-as-an-independent-library"></a>
# ADR 0028: Публикация concurrency-пилота как независимой библиотеки

Статус: принято, 2026-09-07. Квалификация репозиториев ещё не выполнена.

<a id="context"></a>
## Контекст

У `platform-concurrency` уже есть production-потребители в application,
ingest-адаптере и composition root. Планируемый сборщик фидов на Java/Spring Boot
может переиспользовать библиотеку, но его семантика планирования ещё не выбрана.
Распространение не должно превращать IOC-оркестрацию, durable recovery или
Spring-конфигурацию в часть API библиотеки. Владелец проверил основанный на GitHub
namespace Central и выбрал два направления выпуска.

<a id="decision"></a>
## Решение

Публиковать только `io.github.xorex-lc:ioc-platform-concurrency`. Сохранить
существующие Java-пакеты и место в Maven reactor. Остальные модули сохраняют
`com.iocextractor`; это явное исключение для конкретного артефакта при проверке
состава отчётов, а не разрешение добавлять произвольные внешние зависимости
отчётов. Библиотека требует Java 21 и не имеет runtime-зависимостей. Её flattened
consumer POM не содержит parent, неразрешённых свойств или reactor-зависимостей.
Корневой parent и другие platform-модули этим workflow не публикуются.

Допущенная публичная поверхность — двенадцать типов из
[справочника модуля](../../../platform/platform-concurrency/README.md):
асинхронный ограниченный FIFO по ключу, синхронное исключение по ключу, admission
и телеметрия. Ключи локальны процессу; дедупликация, coalescing, persistence,
глобальное ограничение очереди и распределённая координация не обещаются.
Будущая политика фидов требует отдельного решения потребителя. Перед каждым
релизом необходимо проверять совместимость публичных сигнатур и наблюдаемого
документированного поведения. В течение 0.x несовместимые изменения требуют
новой minor-версии и migration notes; patches сохраняют контракт. Перенос
Java-пакетов был бы несовместимым изменением.

Maven Central — основной репозиторий. GitHub Packages зеркалирует точные POM,
основной JAR, sources JAR, Javadoc JAR и подписи. Пилот следует версии релиза
продукта и аннотированному тегу `vX.Y.Z` / `vX.Y.Z-rc.N`, выбранному из default
branch. Независимую периодичность версий можно допустить позже. Публикация
snapshot отложена; локальная сборка snapshot не означает допуска snapshot-репозитория.

Собирать и проверять один раз, без credentials публикации. Сохранять manifest
с source commit и SHA-256 артефактов. Подписывать один раз в окружении
`LIBRARY PUBLISHING`, сохранять подписанный bundle до записей и по умолчанию
использовать стадию валидации Central `USER_MANAGED`. Публикация — отдельная
явная операция workflow. Оба назначения получают те же файлы. Существующие
конфликтующие байты останавливают публикацию; повторные попытки сохраняют
исходный подписанный bundle и deployment ID, пропускают совпадающие файлы и
восстанавливают только отсутствующие файлы назначения. Для восстановления
частичной публикации релиз не перезаписывается, не пересобирается и не подписывается заново.

Независимый consumer находится вне reactor и запускается из временного проекта
с пустыми settings и cache. Он разрешает основные артефакты из одного выбранного
репозитория и проверяет публичное поведение. Каждый публичный репозиторий
необходимо квалифицировать отдельно. Успех локального файлового репозитория —
evidence упаковки, а не доказательство опубликованных координат или интеграции
реального второго сервиса.

<a id="consequences-and-alternatives"></a>
## Последствия и альтернативы

Сохранение библиотеки в этом reactor сохраняет quality gates и ownership.
Отдельный репозиторий или публикация parent для этого пилота не нужны.
Flattening устраняет build inheritance, который не должен требоваться
потребителям. Выпуск только в Central был бы проще, но владелец выбрал второй
канал; сохранённые неизменяемые артефакты и явное восстановление частичной
публикации — цена этого решения. Maven-загрузки из GitHub требуют аутентификации,
поэтому Central остаётся публичным вариантом по умолчанию.

Механика публикации и восстановления описана в
[руководстве оператора](../../guides/library-publication.md). Live-подпись,
авторизация репозиториев и загрузки остаются обязательной квалификацией первого релиза.
